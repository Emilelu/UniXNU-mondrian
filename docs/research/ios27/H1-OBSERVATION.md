# H1 第一次观察（2026-11-22 14:27，镜像 2396f199…）

## 原始观察（用户口述，逐字要点）

1. 菜单里 unixnu 打印的几行字**留着**，持续时间很短，看不清是什么；
2. 然后**屏幕中间出现一个白色的 `|`**；
3. 很快**彻底黑屏**；
4. **完全没有红过**；
5. 没看到 `Exiting boot services…` / `HANDOFF PRE EXIT` / `HANDOFF EXIT CALL` 任何一行；
6. 设备**不会自己复位**（「内核都没起，自动复位更不可能触发」）。

## 这批读数推翻了什么

- **红填没有生效**。`FillScreen(Video, 0x00FF0000)` 在 `HandoffStage(EXIT CALL)` 之前调用，而 `HandoffStage` 走的正是**同一套** `Video[]`/GOP 路径，且它在固件菜单阶段明显是能出字的（观察 1 就证明文本通路活着）。所以「写错缓冲」不再只是猜测候选：**同一条通路，文字能出、纯色填充不出**，最可能是 `FillScreen` 写的那块不是当前扫描输出的那块，或者被随后的显示重配抹掉了（白 `|` 出现在红之后的位置，说明还有东西在画）。
- **绿 bar 也没出现**，`DarwinEnter` 的整屏填充同样不可见 ⇒ trampoline 是否执行**仍然未知**，不能用「没绿」判定它没跑（`Entry.S` 的填充与 `FillScreen` 是同一类直写）。
- **`PRE EXIT` 文字没出现**，而它在 `EXIT CALL` 之前、走 `HandoffStage`。这条比红/绿更有信息量：如果 `HandoffStage` 在菜单阶段能把字画出来，而 `PRE EXIT` 没画出来，那说明**代码没走到 `PRE EXIT`**，或者此时显示已被内核/后来的 `ExitBootServices` 前置动作关掉。这两种可能必须分开，不能合并成「固件没跑到」。
- **白 `|`** 是唯一的新信息：它在终端里出现，说明**有东西在画一个字符**。最可能是文本控制台的光标（`kPETextScreen` 路径的 cursor），也就是 **PE 文本控制台确实初始化了**——如果是这样，内核已经跑过 `pe_init`，这与「XNU 根本没跑起来」的结论相反。这条必须验证，不能想当然。

## 下一步（有先例、可离线准备）

1. **白 `|` 到底是什么**：在 `pexpert/arm/pe_init.c` 与 `osfmk/console/*` 里找画 `|`（或任何单字符光标）的代码路径，确认它是否只在 `PE_initialize_console(... kPETextScreen)` 之后才可能发生。若有明确依据，则「内核已进入 PE 文本控制台」成立，黑屏的原因就变成「文本控制台初始化之后显示被关」。
2. **把红/绿从「直写 FB」换成「走已证明能出字的通路」**：`HandoffStage`（菜单阶段已验证可显示）在 `EXIT CALL` 之后写一行 `AFTER EBS`，若能显示，则 `ExitBootServices` 之后固件仍能画；若不能，则显示在那一刻被关，内核侧必须自己接管。
