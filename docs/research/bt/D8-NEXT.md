# d8 之后要证明什么（2026-11-16）

本页只回答一个问题：**d8 已经证明 PATCH 软件路径返回成功、两次 NVM 尝试均以
`result=-60` 结束；下一步要新增哪一种观测，才能把“NVM 没完成”从现象推进到可判定的
结论？** 它不是 d9 实施方案，不改变预算、下载模式、段长、状态机或地址，也不声称蓝牙可用。
d9 是否飞、飞哪一个单变量，由 Lead 决定。

## 0. d8 已经有的硬事实

证据：`E:/iOS Port/Work/evidence/usblog-20261116-164726/console.log`（3749 行），
`boot.json`（`bootAccepted=true`、`exit=0`、`returnedToFastboot=false`），
`capture.json`（`complete=true`、panic/reset marker 为 null、`stopReason=budget`）。

| 行 | 事实 |
| --- | --- |
| `:495` | `boot: enter speed=3000000 budget=90000ms` |
| `:709` / `:711` | `soc version done e=0`；`QCA controller version 0x12110201` |
| `:1330` | PATCH：`tlv done type=1 segs=602 sent=602 acks=1 final=0 ret=0` |
| `:2778` / `:2781` | NVM 第一次：预算耗尽，`type=2 segs=7 sent=609 acks=7 final=0 ret=-60` |
| `:2803` / `:2806` | fallback：预算耗尽，`type=2 segs=21 sent=630 acks=28 final=1 ret=-60` |
| `:2811` | `[bluetooth] power=1 result=-60 ... tlv_sent=630 tlv_acks=28 tlv_final=1` |

由此只能写：

- PATCH 的 host 调用返回 0，不等于 602 个段都被控制器逐段确认；该次只记录到
  `acks=1`，不能据此说 602 段都有逐段 ack。
- 两次 NVM 都没有 `boot: nvm done`；最后都停在预算耗尽，host 侧返回 `-60`。
- `final` 是 0515 打印的 `stats.tlv_final_status` 累计量（见
  `patches/xnu/0515-k60-bt-tlv-counters.patch:47-51`），**不是**“NVM 完成”布尔值。
  fallback 的 `final=1` 与 `ret=-60` 同时出现，正好证明不能把 `final=1` 当成功。
- `result=-60` 是 host/XNU 的错误码（Linux 宿主脚本里同义错误常显示 `-110`），不是
  控制器内部错误码。

## 1. 三个候选判据

### A. HCI 层 NVM 完成标志

**要新增的观测**：在 NVM 最后一个段之后，控制器主动返回的、可归因于“NVM 下载结束”的
事件/状态（或协议规定的完成响应），并且该观测与 host 的 `e=0`、`tlv_final_status` 分开记录。
不能拿现有 `final` 累计量冒充完成标志；如果协议本来没有这个完成事件，则这个判据不成立，
应记录“协议无此标志”，而不是把超时解释成完成。

- **能排除**：host 单方面认为成功、或预算到期前根本没有收到任何结束响应；
  有完成响应时，可排除“控制器完全没有回应 NVM 结束”。
- **不能排除**：控制器是否真正执行了 NVM、NVM 内容是否正确、RF/时钟/电源是否正常；
  也不能证明 HCI 之上的蓝牙栈可用。
- **代价/风险**：需要在 d9 观测图里增加协议层记录；若没有现成事件，需要改日志或
  读控制器寄存器，必须先由 Lead 批准，且不能顺便改预算/模式/段长。

### B. 控制器执行环境 / 传输状态（exec_env、MHI 或等价状态）

**要新增的观测**：在 NVM 失败后读取控制器内部执行环境或传输状态的可读寄存器/调试接口，
判断它停在 download、exec_env 还是异常状态。Lead 把 `exec_env` / MHI state 列为候选；
但 K60 的蓝牙走 UART，MHI 是 PCIe 侧概念，**先证明本板确实有可读路径**，不能假设存在。

- **能排除**：控制器仍停在下载模式、未进入执行环境，或复位后状态没有推进。
- **不能排除**：控制器内部固件是否完整、NVM 是否被接受、RF 是否工作；
  读状态本身也可能扰动控制器。
- **代价/风险**：需要确认地址/权限/副作用；没有 datasheet 或厂商调试路径时，
  这个判据可能不可用，不能凭猜测的寄存器下结论。

### C. 真实 RX 字节时间线

**要新增的观测**：在 UART TX/RX 上抓真实字节与时间戳，覆盖 PATCH、NVM 第一次、fallback
三段，能区分“没有回字节”“回得很慢”“回了但 host 没等到/没匹配”。这是逻辑分析仪或
等价硬件抓取，不是 console 的 `dt_ms`；console 打印会扰动计时，d8 的 `dt_ms` 只代表
该观测图。

- **能排除**：把“预算耗尽”直接当成“控制器慢”；可区分阻塞、丢字节、DMA/IBS 停顿、
  响应 opcode 不匹配等传输层问题。
- **不能排除**：控制器收到字节后是否执行、NVM 内容是否正确、蓝牙功能是否可用；
  抓到的字节也不等于控制器接受。
- **代价/风险**：需要 Lead 的硬件抓取条件与一次新的设备观测；不能在 bt-agent 侧
  自行开机或改板。

## 2. 判据对照

| 判据 | 新增观测 | 能排除 | 不能排除 | 单变量实验形态 |
| --- | --- | --- | --- | --- |
| A. NVM 完成标志 | 最后段后的控制器完成事件/响应，单独记录 | 完全没有结束响应；host 单方面成功 | 控制器执行、内容正确、RF/电源 | 只加协议层完成记录，不改预算/模式/段长 |
| B. exec_env/MHI 状态 | 控制器状态寄存器/调试接口 | 停在 download/未进入执行环境 | 固件完整、NVM 接受、RF | 只读状态，先证明路径与副作用 |
| C. 真实 RX 时间线 | UART TX/RX 字节+时间戳 | 慢/阻塞/丢字节/opcode 不匹配 | 控制器内部执行、内容正确、蓝牙可用 | 只加硬件抓取，不改下载参数 |

三条判据互不等价：C 解释“为什么 host 等不到”，A 解释“协议上有没有结束”，
B 解释“控制器停在哪”。任何一条成立都**不能**单独推出“NVM 完成”或“蓝牙可用”。

## 3. 和 d8 的对照：哪些解释已经被排除

- 不能再说“`timeout=0` 证明每段正常、65/27≈2.4 s 是慢”：d7 没有逐段计数，
  `timeout=0` 不是段完成数；d8 已用逐段 `e/dt_ms` 证明 NVM 在预算内没有完成。
- 不能再说“`segs=7` / `segs=21` 是全部 27 段”：27 是按 243 B 段长算的理论上限，
  `segs` 只是本次 attempt 的尝试段数，失败尝试也计入；d8 实际第一次 7、fallback 21，
  两者都不是完成总数。
- 不能再说“`sent` 是本次 attempt 的发送数”：`sent/acks` 从 `qbt_boot()` 入口累计，
  fallback 不重置；d8 的 `609→630`、`7→28` 是累计差，不是两次独立总数。
- 不能说“`final=1` 就是 NVM 完成”：fallback 同时有 `ret=-60`，且 `final` 只是
  `tlv_final_status` 累计量。
- 不能说“PATCH `ret=0` 就是 602 段都被控制器确认”：PATCH 的 `acks=1`。

## 4. d9 单变量选择（建议，不是批准）

先问要回答哪一个问题，再选判据；不要一次改两个变量：

1. **如果问题是“预算为什么耗尽”**：优先 C。只有真实 RX 时间线能区分“控制器没回”
   与“回了但 host 等不到/匹配错”；A/B 可以在 C 之后作为解释层。
2. **如果问题是“协议上 NVM 有没有结束”**：优先 A。若协议没有完成事件，就应把
   “无完成标志”本身记录为结论，而不是继续改预算。
3. **如果问题是“控制器是否还活着/停在下载模式”**：优先 B。先证明状态读取路径存在，
   否则这个判据不成立。

无论选哪一个，d9 的 ⑧ 预测必须在飞之前写死：成功看到什么、失败看到什么、
缺日志时如何判“未定位”；不得把“没有崩溃”当成功，也不得把“预算耗尽”自动解释成
“慢”或“卡”。

## 5. 边界

- 本页不是 d9 方案，不包含新代码、补丁、预算/模式/段长/状态机/地址改动。
- 三个判据都不能证明蓝牙功能可用；d8 仍是失败观测，⑧ 的设备格不因宿主用例变绿而改写。
- 宿主 90 个用例只证明冻结源码上的软件契约；它们不属于 A/B/C 的任何一条设备观测。
- bt-agent 不开机、不刷机；设备观测与 d9 由 Lead 执行或明确授权。
