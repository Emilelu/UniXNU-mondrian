**这段前置流程是手工前置，构建器不会替你跑。** `scripts/build-strict.sh` 不执行 `sync-device-input.py` 或 `check-rules.py`，也不强制 clean-tree；它会运行 `git status --porcelain | wc -l`，只将结果记入 manifest 的 `git_dirty` 字段，不据此判定或阻塞。所以下面每一步都必须由 agent 自己按顺序执行，不能假设构建器已经保证。

每次构建前严格按此顺序手工执行（**注意：不是"先跑 check-rules 失败即停"**）：

1. 先 `git fetch origin` 更新远端跟踪引用；确认源仓库 `git status --porcelain` 为空、feature branch 已推送且本地 HEAD 与 `origin/<branch>` 一致。
2. 运行只读 `python3 scripts/sync-device-input.py --check`，逐项检查所有待复制/不同文件，以及"只在构建输入"的额外补丁。差异涉及 build mirror 的本地改动、所有权不明或内容非预期时，先保存原文件/差异并请 Lead 审核，不能直接覆盖；任何额外 `.patch` 都必须停止并交 Lead 审核处理。
3. 只有上一步每项差异都确认应由已提交源文件覆盖、且已保留原有本地内容时，才运行完整 `python3 scripts/sync-device-input.py`（它会写 device/build 输入、所列 framework CLI mirror 和 scratch series）。
4. 再次 `--check`，要求没有待复制项且没有额外补丁。
5. **最后**才运行 `python3 scripts/check-rules.py`；此时应 0 失败，否则停止不构建。

**为什么 check-rules 必须放在 sync 之后（实测）**：给仓库补丁追加一个换行但不 sync 时，`check-rules.py` 直接报 7 条失败（`iron-2`/`hard-5`/`hard-10`/`hard-11` 未提交、`iron-4`/`hard-33` 补丁集指纹、`iron-5` 镜像不一致）。若按"先 check-rules、失败即停"的顺序，agent 在编辑补丁后永远过不了第一关，也就永远走不到 sync——这是死锁，不是严格。

`sync-device-input.py` 不会修改源仓库；所有触摸源码变更必须先提交并从 Windows shell 推送，再同步构建副本。

**为什么必须先检查并安全 sync（因果，不是流程洁癖）**：构建使用 `/opt/k60/trees/usb-cdc-mainline/device/patches/xnu/` 这份构建输入副本。`xnu-inputs.json` 保存构建输入补丁路径及哈希；P-165 对这些记录路径复算哈希，并核对应用数量/输入 series 与仓库 series，但不逐个对照仓库补丁字节。实测：只给仓库里的 `patches/xnu/0616-k60-init-legacy-helper.patch` 追加换行而未 sync，P-165 仍报绿；因此 stale mirror 可能通过 P-165。`--check` 可见待同步、不同文件和额外补丁；先确认仓库改动已提交/推送且 clean，再逐项确认镜像内容覆盖安全，并保留待覆盖的本地状态。完整 sync 还会同步列出的 framework CLI mirror 与 scratch series；额外 `.patch` 须先交 Lead 审核，因为完整同步会删除它们。

4. 写 `build-manifest.json`：设备仓库 branch/HEAD/dirty 文件数（dirty 数只记录、不阻止构建）、series 指纹、构建时间、门禁结果、日志路径、kernel（原始与 payload 内）、payload、boot.img、FD、ADT、DTB 的完整 SHA-256，以及 `payload_args`（从 payload TOML 读回，P-159）。该 manifest 不记录 framework/UEFI/EDK2/build tree 的 Git commit、子模块或工作树状态；这些外部输入的路径、实际命令、HEAD、`git status --porcelain` 与 `git submodule status`（适用时）须另记入每次实验的证据文档，构建前后状态有变化则本次实验作废。
5. 产物与日志在 `E:\k60-work\artifacts\<tag>\`，不污染冻结输入。

`scripts/verify-boot-image.py --manifest M --image I` **实际**检查的范围（以下每条都对着代码核过，不要按更宽的说法写证据）：
1. 按 Android boot header 实际边界解包：kernel 槽是「一个 gzip member（112 B shim + 3,145,728 B FD）+ 其后 4,024 B 裸 DTB」，必须用 `zlib.decompressobj(16+zlib.MAX_WBITS)` 读 `unused_data`（`gzip.decompress()` 会报 `BadGzipFile`）。
2. FD：校验 `fd[40:44] == b'_FVH'`；仅当 `manifest.components.fd` 非空时比较 SHA。payload 与 payload_kernel 同样以 manifest 字段非空为条件，人工确认三字段均有值。
3. kernel 槽尾部 DTB：只校验 FDT magic、FDT 头长度与尾部字节数自洽、长度 ≤64 KiB（P-149）。**不与 `manifest.components.dtb` 比较哈希**；人工提取镜像内 DTB 并与 manifest SHA 核对。
4. ramdisk 槽：仅当 `manifest.components.payload` 非空时比较 SHA；人工确认该字段已填。
5. payload FAT：`Payloads/kernel.macho` 的 sha256 仅在 `manifest.components.payload_kernel` 非空时比较（payload 步骤会改写内核，所以比对的是这一项，不是 `kernel_built`）。
6. payload TOML：扫描每个 `args =` 行，只拒绝 `pong_adsp=1`，允许 `pong_adsp=0` 或缺失。
7. **不检查**：ADT（`manifest.components.adt` 无人读取）、镜像头 cmdline、内核默认参数区，也不比较整个 boot.img 与 `manifest.components.boot_img`。上机前用 mtools 提取 ADT 并人工与 manifest SHA 核对；每次启动前对实际 boot.img 执行 sha256sum，与完整 manifest SHA 比较并记录。参数三处来源仅扫描 payload TOML，其余须人工核。

## 5. 基线通过后的触摸实施顺序

在改任何触摸代码前，先运行 `git fetch origin`，重新运行 `git rev-parse main` 并确认 `git status --porcelain` 为空；本次复核 main 为 `f119a8026776f5dd5d6bf536bb060fc9374c36f3`，相对放行 tag 只有两份文档变化。创建分支时若 main 又推进，先审查其差异；再以当前完整 SHA 创建分支。以读取到的当前完整 main SHA 创建 `feat/touch-power`，从 Windows shell 将分支推送到 origin。先把已放行基线的证据文档、八步记录及生成的中英文 README 表格作为独立 evidence-only commit 提交并推送；确认远端分支同步、工作树干净后，才开始触摸代码变更。

**阶段一的目标是"在健康基线上复现这两个失败"，不是"修坐标"。** 当前放行基线的触摸日志只有 `Goodix initialization failed` 和 `identification failed`，连轮询都到不了；`0x10308/0x10309` 的 off-by-one 是旧的可初始化镜像测出来的历史结论，在当前镜像不复现。先查清 `identification failed` 的当前成因，再谈解析。

**硬停止门槛：** 在触摸/固件/DT 代码修改、strict 构建或候选启动前，必须先以当前设备证据确认可复现的根因，并以官方/同型/反编译证据证明选定实现的具体调用路径、资源/时序与交接保持；还须有确定的失败判据和覆盖关键分支的本地验证方案。仅有嫌疑、类比或 ACK 不能称为"100% 能修复的方案"。任何一项仍未知，就保持只读调查并向 Lead 报告阻塞点，不做试探性实现或候选启动。即使此门槛满足，⑧仍须按 §6 真机验证，不得预先宣称成功。

1. 首先按八步流程调查启动供电路径与当前 probe/DT 初始化失败：核实 regulator provider 的 ABI、DEPEX、入口、资源 ID/PPID、错误处理与交接保持；同时检查 reset 和 SPI。不得猜写 MMIO/PPID，不能假设 IOVDD 已保留就代表芯片上电。
2. 若证据证明额外供电是初始化必要条件，且 provider/ABI 已核实可调用，先实现最小 UEFI 投票与失败日志，完成本地检查后由 Lead 以 fastboot boot 验证 ACK、交接保持和芯片通信；ACK 不代表实测电压或触摸成功。接口无法证实则记录 blocker 并停止，不做猜测性修改。此步必须先于到达轮询的要求。
3. 若供电未被证明是必要条件，不强行加入 UEFI 投票；在证实所需供电状态成立后，重现并定位 identification failed，用当前日志区分 reset、SPI 通路与芯片识别响应。原因不清就停止扩大改动。无论最终是否需要新增供电投票，只要初始化恢复并进入轮询，就必须新增真实且有界的 `Pong touch: POLL hb int=… polls=… reports=… touches=… bad=…` 心跳（例如每 64 次轮询一行）；这是输入验收前置任务，不是可选优化。仅接受通过 BRL 帧校验且包含有效触点的解码结果时才增加 `reports`；INT 上升或总线读次数增加本身不得记为 `reports`。`touches` 应反映当前有效触点，`bad` 记录失败读取/解析；连续报告的 raw 与 normalized 坐标须可审计。
4. 对当前有效 BRL 帧重采原始数据，只有当前读数再次实证偏移才改解析；保持 Mode 0、已验证 GPIO（MISO 17 / MOSI 18 / CLK 16 / CS 19 / RESET 20）、333 kHz。
5. 每次修改重建冻结清单，走 strict 构建/校验/归一启动流程。
6. 不修改 `0340/0391/0401` blob，不编辑 `board.toml kernel_args`，不重排 `series`。
