# PAS1 image carrier decision

> Status: carrier research for feat/adsp-handoff-owner, 2026-11-15. The staged owner/provider APIs exist, but the production carrier and platform PAS/SCM/resource backend do not. This document compares input carriers only; it does not claim PAS1, GLINK, battery, audio, or charging works.

## Decision

Lead selected the kernel-embedded read-only firmware bundle (option B) in E:/k60-work/scratch/reply-adsp-20261115.md:4-15. Lead owns the generator, build switch and assembly data; this branch now implements the bounded reader and owner adapter only. It reuses the repository's existing Metal blob-generation precedent and avoids adding a new UEFI DXE, a fixed physical reservation, or an unimplemented ADT handoff. This selection authorizes reader work, not evidence that an ADSP blob has been generated, linked or exercised on hardware. Lead owns the production carrier. Keep the owner unavailable until the real reader, PAS backend, resource votes, and exclusion are installed and meet the provider contract.

The captured image inputs are 26 files totaling 23,505,092 bytes on disk: adsp.mdt (5,404 B) and 25 present adsp.bNN pieces (23,499,688 B). The complete directory scan found 28 files / 23,506,308 B, including two non-image files. Piece b24 is absent because its segment is pure BSS. The older ADSP-CARRIER.md figure “26 files, 23,494,284 bytes” is the sum of segment file payload copied into memory, not the sum of carrier files; its byte total needs correction before reuse.

The independently summed 0612 segment table has 24 load segments: 23,494,284 bytes of file payload copied and 25,925,684 bytes zero-filled, for 49,419,968 bytes written. The 0x3100000 mapped span is 51,380,224 bytes, including 1,960,256 bytes of intersegment gaps which must remain untouched. The 23,505,092-byte disk bundle exceeds copied PT_LOAD payload by 10,808 bytes: the piece files exceed segment payload by 5,404 bytes because b00 is the 884-byte ELF-header prefix and b25 is the 4,520-byte hash block; adsp.mdt is a second copy of that 5,404-byte metadata. BSS adds 25,925,684 bytes only to the runtime mapped span and contributes no disk bytes. Segment 10 is { 0x86e0b2c0UL, 720, 2672, "adsp.b10" }; its destination is not page aligned, so the loader must honor exact byte offsets/lengths rather than page-aligning or rounding individual copies. The 0612 generated table is fixed at link base 0x86300000 and is not the current relocatable planner; use it only as a reference for copy/BSS arithmetic, not as a loader implementation.

## Reader contract

The production callback declaration is:

~~~c
typedef int (*k60_owner_image_reader)(void *context, K60OwnerImage *image);
~~~

K60OwnerImage supplies a borrowed pointer and byte count for the immutable MDT, a K60AdspMdtPiece callback/context for indexed pieces, an opaque non-null pin handle, and a writable metadata buffer with its capacity. Return exactly 0 only when every field required by the captured MDT is valid and the image is pinned; return nonzero for unavailable, malformed, incomplete, or failed input. A nonzero callback result is normalized by stage 1 to owner-unavailable (-1000); because the owner only calls image_close after a successful reader return, the reader must clean up any partial open/pin itself before returning failure. The owner runs the bounded MDT parser before exclusivity acquisition and before SMEM/TCSR mapping; malformed bounds, missing piece, or exact-size mismatch therefore fails closed without AUTH. The successful pin must remain immutable and valid through every segment copy, BSS operation, cache synchronization, and AUTH decision, not just through the parser call.

The reader must:

- Keep the MDT bytes and every required piece stable for the full image lifetime. Pin/open them consistently so a generation cannot change between MDT metadata and piece reads; image_close releases only the handle acquired by a successful reader, and is called once on safe abort. Poisoned or published ownership retains the image pin.
- Implement the indexed K60AdspMdtPiece(void *, uint32_t index, const uint8_t **, size_t *) callback as a bounded, read-only view. It returns success only with a non-null buffer of the exact planned p_filesz for that piece. Missing files, short reads, truncation, stale metadata, overflow/out-of-range indices, or wrong lengths return failure; never report success with a partial buffer. Any storage-specific chunking must finish and validate the complete piece before exposing it, or retain an immutable backing object whose exact range is available for the subsequent load.
- Provide non-aliased writable metadata storage with enough capacity for the validated prefix plus hash payload. For the captured image this is 884 + 4,520 = 5,404 bytes. Respect parser bounds and do not point the metadata output into the MDT or any piece buffer.
- Perform no hardware access, PAS/SCM call, SMEM/TCSR mapping, boot-argument mutation, or fabricated availability/ownership reporting. Carrier availability is one input to the later platform backend, not proof of authentication or GLINK readiness.

The old K60AdspRead(const char *part, void *dst, uint32_t bytes) in patches/xnu/0612-k60-adsp-image.patch:122 is the same conceptual source-reader boundary: named image part in, exact requested bytes out, zero for success. It is not ABI-compatible with the new reader. K60AdspRead copies into a caller-provided destination in one callback; K60AdspMdtPiece returns a const borrowed pointer and size for a numeric MDT program-header index. A production adapter may wrap files/blob storage in the new interface, but it must preserve exact lengths, errors, immutable lifetime and pin semantics. The old 0612 implementation's generated fixed-address table is not the current relocatable ELF planner.

## Captured-image host fixture

The existing parser test scripts/tests/test-k60-adsp-mdt.py:249-272 can validate the captured MDT and piece inventory offline. It checks MDT SHA-256 1238098817957c4d3cd0995fd413332751ac8082ea315e6e1d9bdb247cadc694; 26 program headers, 24 load segments, hash index 25, prefix 884 B, hash 4,520 B; exact metadata concatenation of 5,404 B; 23 payload-piece callbacks because segment 24 is BSS-only; relocatable span 0x3100000 from link base 0x86300000 to configured physical range [0x9fd00000, 0xa2e00000). The full destination buffer is not allocated or touched by this parser test.

A fake-reader stage test should use these same immutable captured inputs and exercise the reader boundary without pretending to implement the physical carrier. Minimum cases: all MDT/pieces present and exact-size; each required piece missing; short/truncated MDT; short/oversized piece; callback error; out-of-range index; metadata capacity too small; pin invalidation attempted before load; stable pin through all 23 nonzero copy callbacks and the AUTH attempt; and one successful safe-close path. Early carrier/open/initial-parser failures detected before exclusivity acquisition must stop before any SMEM/TCSR/PAS callback. Claim failures at later map/mutex steps can already have invoked those callbacks. A later stage3 reborrow failure stops before AUTH but may follow earlier mapping, stopped FIFO allocation, INIT/MEM_SETUP or prior segment loads; it unwinds or poisons according to stopped-state proof and does not roll back those earlier effects. Fake memory copy can verify the parser plan's 24 destinations, 23,494,284 copy bytes, 25,925,684 zero bytes and exact b10 720-byte placement; this validates host orchestration and arithmetic only. It cannot prove that firmware storage is available during boot, bytes are authentic/trusted, a physical ADSP write/cache maintenance occurred, SCM/PAS authenticated or started a processor, or hardware resources/GLINK are owned.

## Implemented reader boundary

[K60AdspImageReader.h](../../../drivers/PongPower/K60AdspImageReader.h) defines the requested named-copy ABI, contextual reader and K60OwnerImage adapter. Canonical names are adsp.mdt/adsp.bNN; adsp and mdt aliases select the MDT. Reader errors are exact-size/partial read -5, missing carrier/part -6, malformed or out-of-bounds container -7, bad caller arguments -1. They are separate from overlapping MDT/SMEM error enums; owner failures still normalize to -1000 and runtime acquisition failure to -42.

The proposed Lead-facing bundle format is exactly K60A: eight-byte LE magic/count header; count1..64 packed ten-byte LE entries {u16 name_len,u32 raw_size,u32 absolute_offset}; eight-byte canonical names concatenated without NUL; total length at most UINT32_MAX despite the uint64_t symbol. The first body offset must equal align8(8 + 10*count + 8*count); every next body starts exactly at the previous padded end. Every body is padded with zero bytes to8 and the last padded end must equal the supplied length: no extra gaps, appended bytes or missing final padding are accepted. k60_adsp_blob_len is uint64_t and includes every padding byte, not sum(raw_size). Symbols are k60_adsp_blob[] and k60_adsp_blob_len. Missing weak symbols return -6 without dereferencing length or choosing another source. Lead's future generator must conform or agree an explicit version change; no production generator is supplied by this agent.

The full blob is validated before writes: table/name/body bounds, nonzero sizes, duplicates, order/overlap, alignment and padding. Named copies are all-or-nothing and reject writes aliasing source/state. Explicit FAT fallback validates BPB arithmetic before k60_fat_open, walks directories/chains with bounds and refuses fragmented borrowed file extents. It takes an already mapped immutable image supplied by the caller; no DT/physical mapping or automatic FAT fallback was added. All source/metadata/state lifetimes are caller-pinned for the session. Only firmware source bytes are immutable; metadata is writable and disjoint from sources/state, and init/open/close/CAS mutate owner state. Open is a single-session atomic gate; failed double-open preserves the original pins/output, and close applies only to the exact opened image on a safe engine abort.

The actual payload reborrow is stage3 k60_owner_auth_and_start, through k60_adsp_image_segment; build_handoff is stage4 and its final TCSR window remains only serialization+self-parse. Zero-only segment24 invokes load(NULL,0,7245824) without looking for b24. Neither the reader nor host copy tests perform actual ADSP mapping, cache maintenance or authentication.
