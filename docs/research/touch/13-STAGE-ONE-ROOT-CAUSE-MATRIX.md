## Evidence boundaries

- Android reported pm8350c_l2 enabled at 1.8 V. This is not a measurement of rail voltage at the panel during XNU handoff or this boot. The current console explicitly leaves retained IOVDD unverified.
- Historical all-ones and bias-following samples used the former tuple MISO17/MOSI18/CLK16/CS19. They show sampled line values followed configured bias in that setup; they do not establish the current tuple, prove an unpowered controller, or exclude clock, mode, CS, reset, protocol, or wiring faults.
- Live FDT identifies a QUP4 pinctrl group GPIO16-19, not each pad's SPI signal role. Current tuple MISO16/MOSI17/CLK18/CS19 remains an unverified candidate until a valid response is observed.
- The inspected stage-6 path asserts RESET low, calls io_supply_on() (AVDD GPIO71 high followed by 15 ms), configures the clock path, and then sleeps 2 ms before transport setup. bring_up() later releases RESET, waits 100 ms, and reads version/IC info without BRL dev-confirm at 0x10000. There is no explicit 2 ms wait between asserting RESET and enabling AVDD. The official Goodix reference instead enables IOVDD, waits 3 ms, enables AVDD, waits 15 ms, releases RESET, waits 4 ms, performs dev-confirm, then applies its post-confirm reset delay. This is a concrete sequence discrepancy, not proof that the current order is the cause: retained IOVDD is unverified, and exact source lineage from the reference to the K60 Android module is unknown. Local KO strings are not call-order evidence; the subsequent relocation-aware disassembly below establishes a different retained-binary sequence: power-on includes the 100 ms post-reset wait, then its caller performs confirm before version.
- The active patch comments that this is the “Actual K60 goodix_core.ko” sequence and that no boot-option write/read is required. The scratch KO still has no verified acquisition/build lineage or proof of being loaded on this unit. Its relocation-aware disassembly now establishes caller-side dev-confirm after power_on and before read_version; absence inside power_on is not absence from initialization. See [retained KO audit](14-RETAINED-KO-INIT-AUDIT.md). The module caller logs confirm failure and continues, so a fatal new confirm gate would be an intentional policy difference.
- `board.toml` comments say a failed handshake means pads or rails are wrong, not the pin order. The current candidate has no valid handshake and no IOVDD measurement; it cannot distinguish those from reset/order, protocol, or transport faults. Do not use that comment as a failure classifier.
- The completed retained-KO SPI/version audit agrees with the active patch on standard selector-6 framing (F1 + BE32 address + three FF bytes, RX+8) and version checksum (unsigned byte sum of bytes 0..25 modulo 65536 versus LE16 bytes 26..27). This narrows an obvious static framing/checksum mismatch, not GPIO waveform or live-response uncertainty. The retained binary separately retries negative standard SPI transfers and performs up to three version attempts; the active initial probe reads version once. Its explicit all-default-buffer rejection is an additional plausibility policy: a zero-filled version buffer satisfies the additive checksum alone. No current root cause follows from these differences. Exact offsets and limits: [retained KO audit](14-RETAINED-KO-INIT-AUDIT.md).

Its read-only rerun exits 1 (10/11); a count-only raw-frame check can report a pass even when the frame was rejected. This is a verification gap, not evidence that a live frame is valid or that the active parser is wrong. Step 7 remains false; no test file was changed.
- No valid powered BRL frame has been captured. The historical 0x10308/0x10309 offset question is neither reproduced nor resolved on this candidate.

## Regulator semantic check (Linux v6.1 reference)

The lookup result must not be interpreted using a universal auxiliary-data voltage table. Pinned upstream references: https://github.com/torvalds/linux/blob/v6.1/drivers/soc/qcom/cmd-db.c (cmd_db_read_slave_id), https://github.com/torvalds/linux/blob/v6.1/include/soc/qcom/cmd-db.h (accelerator IDs), https://github.com/torvalds/linux/blob/v6.1/drivers/regulator/qcom-rpmh-regulator.c (PM8350C LDO2 hardware data and regulator operations), and https://github.com/torvalds/linux/blob/v6.1/drivers/soc/qcom/rpmhpd.c (ARC corner mapping). Verified anchors (one-based source lines) in those v6.1 files: cmd-db.h lines 9-16; cmd-db.c lines 195-228; qcom-rpmh-regulator.c lines 165-181, 214-235, 640-648 and 885-897; rpmhpd.c lines 572-602 and 643-649. These references describe Linux semantics, not permission to access hardware and not a source match to the installed K60 kernel.

Linux distinguishes ARC (ID 3) from VRM (ID 4). Applying its address-type extraction, (address >> 16) & 7, to the logged 0x42c00 gives ID 4, consistent with VRM; its PM8350C LDO2 definition also selects VRM. The VRM regulator path uses millivolt voltage requests and separate enable/mode controls, not an ARC corner index. The ARC power-domain path explicitly requires ARC before consuming a 16-bit auxiliary corner table. CMD DB itself returns resource-specific auxiliary bytes rather than defining every blob as voltages. Therefore l0=10753 is not an established voltage and idx1800=0->0 is not proof that a 1.8 V vote was encoded or sent.

The historical railh parser converts every matching resource auxiliary blob to little-endian 16-bit levels and its k60_rpmh_level_index() returned success with the last index even when no entry reached the request. Lead commit f354a9d44ee58281f4ea4a324071dcf80f965989 subsequently fixes the latter defect: an unrepresentable request returns K60RpmhNoLevel while leaving the last index as diagnostic output. Its synthetic host test, rerun offline on 2026-11-14 after this fix with KERNEL undefined, prints TESTS OK 16 cases (0 failure(s)), including request 9999 returning NoLevel. The broader auxiliary-schema issue remains: the fixture supplies assumed millivolt levels and does not validate the live ldoc2 blob schema. These are interpretation discrepancies, not evidence that a wrong vote was executed: the reviewed probe has no vote operation. Before any separately authorized provider implementation, Lead must bind ldoc2 to the actual PMIC/DT resource, verify accelerator type and the exact platform schema, and distinguish a command ACK from physical voltage. Do not turn the logged index or unexplained auxiliary bytes into a hardware command.
