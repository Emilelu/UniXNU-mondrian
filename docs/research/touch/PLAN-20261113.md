`scripts/verify-boot-image.py --manifest M --image I` **实际**检查的范围（以下每条都对着代码核过，不要按更宽的说法写证据）：
1. 按 Android boot header 实际边界解包：kernel 槽是「一个 gzip member（112 B shim + 3,145,728 B FD）+ 其后 4,024 B 裸 DTB」，必须用 `zlib.decompressobj(16+zlib.MAX_WBITS)` 读 `unused_data`（`gzip.decompress()` 会报 `BadGzipFile`）。
2. FD：校验 `fd[40:44] == b'_FVH'`；仅当 `manifest.components.fd` 非空时比较 SHA。payload 与 payload_kernel 同样以 manifest 字段非空为条件，人工确认三字段均有值。
3. kernel 槽尾部 DTB：只校验 FDT magic、FDT 头长度与尾部字节数自洽、长度 ≤64 KiB（P-149）。**不与 `manifest.components.dtb` 比较哈希**；人工提取镜像内 DTB 并与 manifest SHA 核对。
4. ramdisk 槽：仅当 `manifest.components.payload` 非空时比较 SHA；人工确认该字段已填。
5. payload FAT：`Payloads/kernel.macho` 的 sha256 仅在 `manifest.components.payload_kernel` 非空时比较（payload 步骤会改写内核，所以比对的是这一项，不是 `kernel_built`）。
6. payload TOML：扫描每个 `args =` 行，只拒绝 `pong_adsp=1`，允许 `pong_adsp=0` 或缺失。
7. **不检查**：ADT（`manifest.components.adt` 无人读取）、镜像头 cmdline、内核默认参数区，也不比较整个 boot.img 与 `manifest.components.boot_img`。上机前用 mtools 提取 ADT 并人工与 manifest SHA 核对；每次启动前对实际 boot.img 执行 sha256sum，与完整 manifest SHA 比较并记录。参数三处来源仅扫描 payload TOML，其余须人工核。

1. 首先按八步流程调查启动供电路径与当前 probe/DT 初始化失败：核实 regulator provider 的 ABI、DEPEX、入口、资源 ID/PPID、错误处理与交接保持；同时检查 reset 和 SPI。不得猜写 MMIO/PPID，不能假设 IOVDD 已保留就代表芯片上电。
2. 若证据证明额外供电是初始化必要条件，且 provider/ABI 已核实可调用，先实现最小 UEFI 投票与失败日志，在独立 firmware feature branch 提交并推送，完成本地检查后，由 Lead 构建并归档含该变更的新 FD，记录完整 source/FD SHA，再显式作为 strict 的 --fd 输入；必须证明该 FD 实际进入 boot.img。继续复用 cf448571 旧 FD 不会带入任何新 UEFI 投票代码，不能拿它验证固件改动。新 FD 未获 Lead 放行（含 P-154/启动安全验证）前停止，不自行替换已知可启动 FD。随后才由 Lead 以 fastboot boot 验证 ACK、交接保持和芯片通信；ACK 不代表实测电压或触摸成功。接口无法证实则记录 blocker 并停止，不做猜测性修改。此步必须先于到达轮询的要求。
3. 若供电未被证明是必要条件，不强行加入 UEFI 投票；在证实所需供电状态成立后，重现并定位 identification failed，用当前日志区分 reset、SPI 通路与芯片识别响应。原因不清就停止扩大改动。无论最终是否需要新增供电投票，只要初始化恢复并进入轮询，就必须新增真实且有界的 `Pong touch: POLL hb int=… polls=… reports=… touches=… bad=…` 心跳（例如每 64 次轮询一行）；这是输入验收前置任务，不是可选优化。仅接受通过 BRL 帧校验且包含有效触点的解码结果时才增加 `reports`；INT 上升或总线读次数增加本身不得记为 `reports`。`touches` 应反映当前有效触点，`bad` 记录失败读取/解析；连续报告的 raw 与 normalized 坐标须可审计。
4. 有效通信恢复后重采当前 BRL 原始帧，只有再次实证偏移才改解析。当前源配置的 `bitbang-pins` 为 MISO16/MOSI17/CLK18/CS19，reset20、INT21；这是引用 SM8475P 80-27620-1 Rev.AJ Table 2-4 及 pinctrl 的新角色解释，不是已获芯片响应的硬件定论。必须分别保存 QUP4 pad-group 与 SPI lane-role 的原始证据（含 L0/L1 方向约定），并与旧 MISO17/MOSI18/CLK16/CS19 的历史记录对账；总线默认字节不能裁决两者。当前 tuple 仅标为待端到端验证，不盲回退旧 tuple、不再做无证排列扫描。保持现有 Mode 0 及有来源的时序；半周期 2 µs 仅为源配置，实际频率还受 bit-bang 开销影响，不写成已实测 333 kHz。
5. 每次修改重建冻结清单，走 strict 构建/校验/归一启动流程。
6. 不修改 `0340/0391/0401` blob，不编辑 `board.toml kernel_args`，不再擅改 `series`。本分支已发生 e0825c6 的六条 probe 摘除，这是待复核的历史改动，不是本计划给出的追加授权；保留证据，交 Lead 核对既有许可与本次实际 series，不擅自还原或继续摘除。

## 6. 验收

- 第⑧步判据：控制台出现 `Pong touch: POLL hb int=1 ... reports>0`；同次启动连续 3 个心跳样本的累计 `reports` 严格递增、每段至少增加 1，并附可关联的有效 BRL 触点坐标。raw 坐标须在 14400×32000 范围内，normalized 坐标在 0..65535，按比例映射回 1440×3200 屏幕范围。屏幕必须实际响应触摸并由 Lead 录屏；健康启动原始日志、manifest 与启动前核验的完整镜像 SHA 可复核。缺少新增心跳不得验收或以旧证据替代。
- 构建/镜像测试：构建失败即退出、marker 过期、缺 FD、组件哈希不符、容器截断、`pong_adsp=1` 拒绝 / `0` 允许、冻结项变化拒绝。
- 采集判定测试：分别覆盖 `panic(`、Debugger、`K60CACHE FAIL`、initproc、`K60PANIC: ring kept`，主动与被动 K60PAS、零字节日志、普通截断与符合条件的 budget-complete。`K60PANIC: restart windows ready` 不应被当作 panic。
- BRL 测试：16-bit tail checksum 与 reset 语义、DT 缺失/宽度/类型拒绝、仅 INT 上升不改 `reports`、空帧/越界/多点/松手/传输失败。历史 "10/11" 不再作绿灯。
- 按 §2 区分提交/安全同步、重建前旧 stamp 与构建后验证。提交前运行 `sync-device-input.py --check`、`check-rules.py` 并记录可解释的预期差异；只有 Lead 明确登记的重建型旧 stamp 阻塞可留待构建刷新，不得称为通过，也不能扩展为其他规则豁免。构建后在无 `K60_BUILD_IN_PROGRESS` 环境完整门禁必须全绿，启动前 clean-tree 与 branch/remote parity 必须重新核验。英文代码/文档分开提交推送，push 用 Windows shell；已发生的 evidence/code 顺序按 §5 审计，不通过补写伪造既有合规。
