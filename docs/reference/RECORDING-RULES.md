## 1. 什么时候必须动笔

| 时机 | 必须的动作 |
|---|---|
| 每解决一个问题（哪怕很小） | **当场**追加一条 ISSUES；坑形态典型的同步追加 PITFALLS |
| 每做一个「这么干而不是那么干」的决定 | 当场追加一条 DECISIONS |
| 每次上机取证后 | 结果写回触发它的那条 ISSUES/DECISIONS 的「验证」栏；新事实够独立就开新条 |
| 每次构建出要留存的镜像 | sha 落进 `candidates/<目录>/build-verification.json`（打包脚本自动做），并在 DECISIONS「镜像身份链」对时 |
| **交接前（任何 agent 收工）** | **刷新 `INDEX.md`**（新文档登记、状态档更新）+ 在主交接文档写清「下一步第一件事」 |
| 发现旧文档叙述被推翻 | 不删旧文档；在 INDEX 对应条目改状态档 + 写明被什么推翻（见 §5） |

**禁止**：凭记忆口头交接、把结论只留在会话里、「等做完一起写」。

## 2. ISSUES 条目模板（字段固定，照抄）

```markdown
### I-YYYYMMDD-NN <一句话标题>

- **现象**：可观察到的行为（含关键日志行原文，用代码块）。
- **证据**：实物链接——日志路径、屏幕照片、build-verification.json、源码 file:line。没有实物标「待验证」。
- **根因**：已证实写结论；未证实写「未定」+ 已排除项。禁止把猜测写成根因。
- **修复**：改了什么、在哪（file:line / 候选目录 / boot-arg）。
- **验证**：怎么证明修好了（探针输出、屏幕实测、sha）；未验证写「待验证」。
- **相关 commit / 文档**：分支、commit、DECISIONS/PITFALLS 交叉引用。
- **回归判定**：以后怎么 30 秒内确认它没复发（一条命令 / 一个探针值 / 一行日志）。
- **影响面**：波及哪些子系统。
- **遗留风险**：还没排干净的尾巴。
```

规则：
- 编号 `I-YYYYMMDD-NN`，NN 当日递增，**只增不改**；已关闭的条目不删除，移到「已解决」区。
- 证据必须可复查：路径、行号、sha256 三选二。屏幕观察必须注明「照片存档路径」或「无照片，待验证」。
- **根因未定是合法状态**，写「未定」比写错强。

## 3. DECISIONS 条目模板

```markdown
## D-YYYY-MM-DD-NN <决定的一句话>

- **日期**：
- **背景**：为什么需要决定。
- **证据**：依据的实物（日志/源码/实测）。
- **决定**：选了什么，明确排除了什么。
- **验证方式**：怎么知道这个决定是对的（或已证伪）。
- **回滚方式**：怎么撤销（备份文件/分支/boot-arg 开关）。
- **相关文件**：
```

规则：时间倒序，新条目放最上；没有回滚方式的决定不允许落地（「不可回滚」本身也要写出来并说明理由）。

## 4. PITFALLS 条目模板

症状 / 触发条件 / 为什么当初走错 / 正确做法 / 证据 / 30 秒判定——六字段缺一不可，格式见 PITFALLS.md 现有条目。

## 5. 过时叙述的处理（不删，标注）

1. 旧文档**不删不改**（历史档案价值）；在 `INDEX.md` 把状态档改为「部分过时」或「已作废」，并**写明被哪份新证据推翻**。
2. 典型已被推翻的叙述（禁止再当真）：「内核未重编」（HANDOFF-2026-11-02 §4，20:42 已重编）、「AP 只能访问 2 GB」（HANDOFF-FULL-2026-10-25）、「XNU 未开始」（PORT-STATUS-K60）、「注册 Sandbox 替身能止崩」（DIAGNOSIS-SANDBOX 隐含假设）、「Data 256 MiB ENOSPC」（DATA-SPACE，已扩 2 GiB）。
3. 发现自己被旧文档误导时：除了更新 INDEX，还要在 ISSUES 补一条「文档误导」记录（参照 I-20261102-05），防止下一个人再踩。

## 6. 写作纪律

- **只写有证据的**；推断、用户转述、记忆全部标「待验证」。
- 引用二进制身份只写 sha256（至少前 8 位），**从 build-verification.json 抄，不凭记忆**（PITFALLS P-06）。
- 路径写全（含盘符或 `~/hackios/...`），WSL 与 Windows 路径不混写。
- 设备序列号写进证据（当前 UniXNU 路线机器 = `6033dbec`；hackios 仓旧记录 = `ffec9d48`，两台机器）。
- 篇幅不限，但每条第一句话必须能独立读懂结论。

## 7. 识图纪律（屏摄读数，强制流程）

> **硬前提：XNU 阶段没有任何日志通道。** XNU 接管后 USB 全断；ramoops 通道即断、重启不保留、且只属加载器/DXE 侧（ISSUES I-20261103-02）；USB 日志通道（apps_smmu stream 0）尚未打通（I-20261103-04）；串口 COM3/COM4 是蓝牙虚拟口。因此 XNU 阶段的证据**只有屏摄一种来源**——禁止在流程里写「优先读文本源/日志」，禁止向用户索要 XNU 阶段日志文件（对应坑：PITFALLS P-10）。

1. **一律标注**：屏摄的数字/hex 读数默认标「**屏摄读数、低置信**」；经用户逐字核对后才升格为事实。
2. **三重一致性校验**（任一不过 → 降级「待核对」，禁止只凭单字辨认数字）：
   - 上下文一致性：心跳 `t` 步进恒 15；`abn` 单调递增；`kxq ≈ abn`（±1）；`xp ≈ abn − 4`；`kxp` 恒定 5；
   - 相邻行差分：同字段前后两行做差，差值必须是预期步长；
   - 同帧交叉：同一数值在别处重复出现时（如 `dw=`），必须一致。
3. **易混对**：`0↔8`、`3↔8`、`5↔6`、`1↔7`、`2↔8`。凡末位落在这些对 → 一律「待核对」。
4. **长 hex 禁止肉眼数位数**：指针/地址应为 16 位 hex；`0x…` 常见宽度 4/8/16 位。先按每 2 位分组核对，再与字段语义比对（`xstat=0x0` 1 位、`v_flags=0x84801` 5 位、`rf=0x0` 1 位）。长度与语义不符（含连续重复字符如一串 `f` 的个数）→ 写「**位数不确定**」，**不给具体值**。
5. **单点读数低置信**：同一 hex 值至少两处交叉验证（不同行/不同上下文长度与内容完全一致）；只出现一次 → 「单点读数、低置信」。
6. **先裁切放大再读**：可疑区域（数字列、行尾字段）单独裁出放大；按行带（上/中/下）分段放大；禁止整屏缩放后直接读数字；挖孔截断不作证据（PITFALLS P-08）。
7. **已知真值优先**：用户已核实的值（`t=135 abn=382`、`KE 38` 作废、顶行 `KXP 24`）落入证据索引后，同一字段不再按图像重推。
8. **问用户只问判断题**：一次一个是/否问题（例：「`abn` 是 382 吗？」），不请用户重读整行。
9. **三选一证据判据（硬规矩，2026-11-04 立，与 PITFALLS-FROM-HISTORY 第 32 条同文）**：任何作为结论依据的行、寄存器值、sha、编号，必须满足以下之一才可用作证据——**① 用户明确确认过；② 从设备/文件回读的真值；③ 原始日志文本。三者都没有时，禁止写结论，只能写「观测不清，待核」。** 其中**地址类读数（panic / fault / 回溯地址）是最高危一类：必须经用户核对后才允许用于符号映射与归因**，引用时在文档中标注「地址来源 = 用户核对屏摄」（符号映射按地址计算，错一位即归因到错误代码）。违反实例（识图误读六连：`abn=382→302`、`7 个 f→6 个`、`verify=ffffffff` 读成乱码、`n=9/op=28→n=3/op=2b`、`result=00000000→0008b800`、panic 地址 `0xfffffff007ad3ac0→0xfffffff807add3ac0`）见 PITFALLS-FROM-HISTORY 第 32 条。

## 8. 每坑必录（会话收尾强制检查点）

> 用户 2026-11-03 硬要求：「踩的所有坑都要写到文档里面，不要每次都让我说」。

每次会话收尾前，收尾者必须自检三连问：

1. **本轮踩的坑是否已全部落 PITFALLS？**（含「差点踩了但被闸门拦住」的未遂坑——未遂坑同样有记录价值。）
2. **新坑是否当轮写入？** 不得等用户提醒、不得「等收尾一起写」；坑不论大小一律记录（30 秒能判下次要不要避的，就够格）。
3. **编号与交叉引用是否闭合？** PITFALLS ↔ ISSUES ↔ DECISIONS 三处互引的编号真实存在；坑条目的证据栏有实物（文件+行号/sha/日志路径）。

收尾自检不过 = 会话不许收工。漏录被用户补指出的，本身也记一条（元坑：漏录）。
