## 为什么这次冻结不是保守

1. **唯一在用的仪器是无效的**：ramoops 镜像在断电/复位后不保留（P-307，用户当场指出）。
   读卡器在 DXE 里读的是「刚刚被复位清掉」的窗口，所以它读到的永远是空 —— 它证明不了任何事。
2. **黑屏发生在固件交棒之后、任何输出之前**：没有一份日志能定位它是死在
   `arm_init` 之前、`arm_init` 之后、还是 `bsd_init`。三次飞行都是 0 字节（P-300）。
3. 在 1、2 未解决之前，每次飞行只能得到同一个观测：黑屏。这不是信息，是重复。

## 解冻的必要条件（缺一不可）1. **同一次启动内的日志通路**：移植 16 线的 `0300`（`bsd/dev/k60_usblog.c`，CDC-ACM EP0）
   与 `0243`（console export），使内核在**运行时**把字送出去；判据是
   `check-kernel-console.py --flight` 之外再加一条「符号 + 端点 + 首次写成功自报」三连。
2. **或者**屏幕侧可读：内核在 `arm_init` 之后立刻用帧缓冲打点（绿条之后的第一行），
   使黑屏前至少有一行可见证据。
3. 上述任一通路在**离线**验证通过（符号、端点描述符、缓冲区地址、失败路径各一份证据），
   并且 `IOS27-FLIGHT-BLOCKERS.toml` 只剩「运行期未知」而不再有「无法观测」。
4. **自动引导**：固件菜单超时必须恢复（`[payload] timeout` 设为正数，落到指定的 27 条目），
   不允许任何人再手动选择条目。用户 2026-11-22 03:04 明确表示不会再手动操作。
5. **自动复位**：内核死掉后设备必须自己回到固件（或 fastboot），不需要长按电源。
   做法是跳转前由 DarwinBoot 武装一个硬件看门狗（PMIC/AP WDT），超时未被内核「接手或关闭」就复位；
   这样一来「菜单超时 10 s → 内核 → 若死则 N 秒后自动复位 → 再进菜单」构成无人值守回路。
   判据：连续两次无人值守循环后，证据目录里出现两个独立 boot 记录，
   且第二次的读数器（或 EP0 日志）能证明设备确实自行复位过（时间戳 + 复位原因）。
