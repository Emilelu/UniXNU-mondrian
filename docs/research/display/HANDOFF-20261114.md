### 默认镜像（不传 backlight 参数，必须首先满足）

   `... published level 2047 dbv 0xff control 0 (no AppleARMBacklight conformance)` 出现。
2. IORegistry 出现 K60Backlight，带 `IODisplayParameters.brightness{min 0,max 2047}`，
   **不带** `backlight-control`。
3. SpringBoard 正常（日志 > 100 行）、`K60 DISPLAY: first frame presented` 出现、
   backboardd 段错误次数为 0。
4. `native_backlight_stats`：[0]=3、[1] 随系统请求递增、[5]=0、[15] 递增；
   `native_backlight_request`：[4]=0、[5]=0。逐索引见 `STATS-INDEX.md`。
5. min/mid/max 三档：`stats[2]`/`stats[4]` 互不相同，且屏上可见亮度变化；
   FadePeriod 渐变平滑（无跳变）。
6. 屏幕持续更新（无 int-236 停更）。

### 第二段（可选，只在默认镜像通过后才试）

stats[0]=4、request[4]=1、request[5]=1。若此配置下 backboardd 再崩，则判定「发布
backlight-control 本身不安全」，默认镜像仍是交付形态，P-62 的保守结论维持。

## 构建期间的两条硬教训（2026-11-15 实测）
1. **构建窗口内不要改任何被 git 跟踪的文件**。brightness-7/8 的 kernel 都编成功了，却都在 payload 步骤被 registry 拒：iron-2/hard-5/hard-10/hard-11 报「N tracked file(s) modified but not committed」。registry 在 payload 前会重跑，跑一次构建要 8～10 分钟，尾段才发现白费。
2. **构建开始前一刻必须 git fetch + rebase**。别的线一直在推 main：brightness-8 就是构建过程中 main 前进了 1 个提交，payload 被「HEAD is 1 commit(s) behind origin/main」拒掉。做法是 fetch → rebase → 同步 device input → 立刻起构建，中间不插入任何编辑。
