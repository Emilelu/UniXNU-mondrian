## 4. 三个已解决的硬阻断（含证据，别重复踩）

### 4.1 SpringBoard `exception=6` / `FBSDisplayMode ... infxinf@0x`

**症状**
```
Pong UI Crash: SpringBoard[110] exception=6 code=0x1/0x1de8c2bd4 ...
x0 text=FBSDisplayMode cannot be configured as requested:
   <FBSDisplayMode: 0x283b1a170: infxinf@0x (1440x3200/0) 60Hz p3 SDR>
```

**根因链**
ADT `/chosen` 里没有 `display-scale`
→ FrontBoard 取到的 `preferredScale = 0`
→ 点尺寸 `1440 / 0 = inf`
→ SpringBoard 在 `-[FBSDisplayMode _initWithWidth:height:preferredScale:...]` 里主动 `brk`（**不是内核跑飞**）

**修复**：`profiles/os/ipados-16.6.1-20G81/profile.toml` 的 `[adt."chosen"."u32"]` 加 `"display-scale" = 3`（1440×3200 → 480×1066.67 点）。提交 `db7177c`。

**验证方式**：payload 内 `kernel.macho.adt` 里 `display-scale` 位于 offset 9536，`len=4 value=3`。**注意 ADT 不是标准 FDT，`dtc` 会报 `Blob has incorrect magic number`，只能用字节搜索验证。**

### 4.2 `send_resource_violation(CPU wakes, ...): error 0x10000004` 刷屏

**根因**：`osfmk/kern/task.c` 里该 `printf` 位于 `disable_exc_resource` 提前返回**之前**；且板上没有 violation port，`send` 返回 `0x10000004`。boot console 与 UI 共用同一块 software framebuffer，刷屏直接把进度条盖掉。

**两条修复路径（都在仓库里）**
- 源码级：`patches/xnu/0230-k60-exc-resource-early-out.patch`（已提交 `6db2954`，在 `series` 里）
- 二进制级（**当前实际生效的是这条**）：`smp/patch-violation-printf.py`，把三条格式串首字节改 `\0`

三条被清空的串：
```
send_resource_violation(CPU wakes, ...): error %#x\n
send_resource_violation(disk_writes, ...): error %#x\n
send_resource_violation(CPU usage, ...): error %#x\n
```

> 注意：二进制里还有一条 `send_resource_violation(disk_writes, ...)\n`（**不带** `error %#x`，在 offset 1259407），那是另一处调用点的文本，**不要误清**。

### 4.3 watchdogd

launchd disabled-jobs 策略写 `/private/var/db/com.apple.xpc.launchd/disabled.plist` 禁 `com.apple.watchdogd`（补丁 0222）。

## 5. 当前卡点：进度条推进极慢

### 已知现象
- 黑底 + 进度条界面，与「像加了一层模糊遮罩的跑码界面」**交替出现**
- 进度条**有动静**，但极慢；可能停在固定位置
- 日志不可读（两个绘制源抢同一块面板）

### 已定位的原因（部分）
`MiniIOMobileFramebuffer` 是**纯软件** framebuffer：
- 每帧要对 1440×3200×4 ≈ **18.4 MB** 做 bilinear 缩放 + memcpy
- `fb_threads` 默认 **1**（`MiniIOMobileFramebuffer.cpp:165`），单核缩放整帧约 **9–10 ms**
- 代码注释写「Three by default」但 `TUNABLE` 默认值实际是 `1` —— **注释与代码不一致，以代码为准**

日志里那条周期性输出：
```
MiniIOMobileFramebuffer: %u frames in %llu ms (%llu a second), %llu us each in the driver,
after %llu us waiting for the GPU and, %u of them, %llu us for the next refresh; ...
```
出自 `MiniIOMobileFramebuffer.cpp:1001`，**每 5 秒一条**。用户看到的 "waiting for gpu" 就是这条，**不是 GPU 真卡**。

### 尚未确认
- 进度条是**真的在推进**，还是只是 `vc_progress` 的转圈动画
- 是否卡在某个 launchd job（datamigrator / mobileassetd / SpringBoard 首帧）
- 交替刷屏是否影响实际进度

### 建议的下一步（**都是 boot-arg，不用重编内核**）

```bash
--kernel-arg fb_threads=3        # 三核并行缩放，帧耗时 9ms → 约 3ms
--kernel-arg k60_fontscale=3     # 控制台字体放大 3 倍，日志才看得清（2~4 有效）
--kernel-arg fb_hz=60            # 保持 60，先别动
```

> `k60_fontscale` 实现在 `video_console.c:2831`，`fb_threads` 在 `MiniIOMobileFramebuffer.cpp:165`，两者都已在当前内核里，**加 boot-arg 即可生效**。

## 6. 构建

### 6.1 内核源码构建目前**不可用**（重要）

`./unixnu build kernel` 在本机 WSL 上卡在 xnu 的 SETUP 主机工具与 `mig`，与业务代码无关：

| 问题 | 现象 | 修法 |
| --- | --- | --- |
| SETUP 工具找不到 `stdio.h` | `'stdio.h' file not found`，因为 `MakeInc.cmd:307` 在 `HOST_CC` 未定义时回落到交叉 clang | `export HOST_CC=/opt/unixnu-linux/CommandLineTools/usr/bin/xnu-host-cc`（**已验证有效**） |
| `mig` 第 183 行 `: command not found` | `C=${MIGCC}` 为空，`"$C" -E ...` 展开成空命令 | **未解决**，见下 |

`MIGCC` 失败的准确位置：
- `MakeInc.cmd:195-196`：`ifeq ($(origin MIGCC),undefined)` → `export MIGCC := $(CC)`，而该点 `$(CC)` 为空
- 试过在 `$TREE/scripts/build-xnu-4k-baseline.sh` 顶部插 `export MIGCC=...`，**被 unixnu 重建 tree 覆盖**
- 正解方向：改 `scripts/unixnu/kernel.py` 的 `linux_env()` 加 `MIGCC`，或修 `/opt/unixnu-linux/CommandLineTools/usr/bin/mig` 的兜底（该文件 root 所有，需要 sudo）

### 6.2 现在能用的构建路径（只换 payload / bootimg，不编内核）

```bash
# 用现成 kernel.macho，只换 ADT 和 boot-arg
./unixnu build payload -D ~/hackios/UniXNU-mondrian \
  --kernel /tmp/km-quiet.macho \
  --trust-cache ~/hackios/UniXNU-mondrian/prebuilt/20G81-trustcache.bundle \
  --kernel-arg pong_data_mount=1 --kernel-arg pong_data_rw=1

./unixnu bootimg -D ~/hackios/UniXNU-mondrian --uefi ~/hackios/uefi-mondrian \
  --fd ~/hackios/uefi-mondrian/Build/mondrianPkg/DEBUG_CLANGPDB/FV/SILICIUM_UEFI.fd \
  --dtb $OUT/device-tree/hardware.dtb \
  --ramdisk $OUT/payload/payload.img \
  -o /mnt/d/Android/k60-ios/boot-xxx.img
```

**`bootimg` 最后会打印 `boot image header does not match the requested parameters` —— 这是误报**（内部校验假设 legacy header，而 Pong 是 v4，header_size=1584）。用独立校验确认：

```bash
bash ~/hackios/UniXNU-mondrian/scripts/verify-k60-boot-img.sh /mnt/d/Android/k60-ios/boot-xxx.img
# 期望：RESULT == PASS
```

## 7. 红线（违反会毁设备）

1. **`fastboot boot`，永远不要 `fastboot flash boot`。**
   boot 分区属于 Android，flash 会毁掉双系统。`boot` 只把镜像读进内存临时启动，不写任何分区。
2. **`persist` 分区绝对不能刷写**，会触发 TEE `deleteAllKeys`，密钥永久失效。
3. 一次只改一个变量，改完必须能说清"这次和上次差在哪"。

## 8. 下一步优先级建议

| 优先级 | 任务 | 理由 |
| --- | --- | --- |
| P0 | 让进度条可观测（`fb_threads=3` + `k60_fontscale=3`） | 现在完全看不见卡在哪 |
| P0 | 修内核源码构建（`MIGCC`） | 后面所有改动都要重编内核 |
| P1 | **GPU（Adreno）** | 软件 framebuffer 是当前性能天花板，120 Hz 无从谈起 |
| P1 | 120 Hz | 依赖 GPU + DSI 时序，`fb_hz` 只是软件节拍，**改不了面板刷新率** |
| P2 | 触摸 | 进度条卡住时可能需要交互 |
| P3 | 音频 / 网络 / 相机 | — |

### 关于 GPU 的现状

- `drivers/PongAdreno/`（含 `submit/`）源码已存在，**未进链接**
- 当前生效的是 `patches/xnu/0212-k60-empty-accelerator.patch`：一个空 `IOAcceleratorES`，让 backboardd 的 `IOServiceMatching("IOAcceleratorES")` 能匹配上，否则合成帧全黑。boot-arg `accel_stub=0` 可关
- `scripts/` 下已有一批 Adreno / Metal / Turnip 相关工具，**接手时先盘一遍再动手**：
  `build-adreno-metal-bridge.py`、`build-adreno-metal-plugin.py`、`build-adreno740-accelerator.py`、`build-native-adreno-accelerator.py`、`build-pong-adreno-platform.py`、`build-pong-turnip.py`、`build-pong-metal-plugin.py`、`audit-target-iogpu-*.py`、`audit-target-metal-*.py`
- `patches/` 下已有 `mesa`、`metal2vulkan`、`libpthread` 三个目录

### 关于 120 Hz 的现实

`fb_hz` 只改 `refreshHz()` 的返回值，影响的是：
- 发布给 CoreAnimation 的 `TimingElements` 刷新率
- vsync 定时器周期（`MiniIOMobileFramebuffer.cpp:1172`）

它**不会**改变面板的 DSI 时序。真正的 120 Hz 需要：
1. 显示控制器侧配置（PongUfs / DSI 驱动）
2. GPU 合成（软件路径下 120 Hz 意味着每帧 8.3 ms，单核缩放一帧就要 9–10 ms，**不可能**）

所以顺序必须是 **GPU 先行，120 Hz 后置**。

## 11. 交接时必须知道的三件事

1. **别信"已经修好了"，先上机验证。** 这一路上有三四次「日志看着像修好了，其实是上一个镜像没换」。
2. **一次只动一个变量。** `display-scale` 和 printf 静音是分两次验证的，中间那次 `boot-quiet.img` 因为内核编译失败、脚本没停，实际是旧内核重打包——差点误判。
3. **含变量的命令写进 `.sh`。** `HOST_CC` 就是这么丢的：交互式跑过一次，写成脚本时忘了带。
