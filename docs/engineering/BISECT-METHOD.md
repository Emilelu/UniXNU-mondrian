# 单变量二分法（跨线通用）

这份文档只写**方法**，不写任何一条线的硬件结论。它是
`docs/research/bt/S4-SPEC.md` §7.17 的跨线版本，供 adsp / modem / wifi 等线直接引用，
不必各写一遍、各错一遍。三个反例只用已有的提交号与 evidence 路径，不新增观测。

适用范围：一条配方里同时有多个可疑改动、而设备只有一台、一次只能飞一张图的场合。

---

## 一、五步

### 第 1 步：先把变量定义清楚

每个改动块（hunk / patch / boot arg）必须**只做一件事**，并且能用一句话说清它改的是
"哪一层"（门闩？时序？判据？）。

然后为每个块生成**单块补丁**，并用字节级等式校验它确实是"全量减其余"：
`全量补丁 − 其余 N−1 块 = 这一块`。校验不做，后面每一格的归因都建立在假设上。

反模式：一个块里顺手改两件事（"反正都要改"），之后这一块永远无法单独排除。

### 第 2 步：判据先写死，再飞

判据要在飞之前写进配方说明，而且必须是**与可疑子系统无关的外部判据**。

- 好判据：到桌面（SpringBoard 计数 > 100）、控制台是否出现、串口是否被枚举。
- 坏判据：可疑子系统自己的日志。被观测对象可能整段不跑——那不是失败，是没被观测到。

反模式：拿"有没有 XXX 驱动打印"当存活判据；该 hunk 恰好把打印拿掉时，结论会完全反过来。

### 第 3 步：每格都要飞；飞过的要能查

二分的代价是"格数 × 一次飞行"。少飞一格，矩阵就有一个洞，而洞经常正好是决定性的那一格。

**规矩：二分要么飞满，要么在矩阵里显式标出"已构建未飞"。**

可查性靠工具而不是靠记性：拿每张图的 `build-manifest.json` 里的 `boot_img`
与 `evidence/*/boot.json` 里的 `imageSha256` 做差集，就能列出"构建完但没飞"的镜像
（本仓库实现：`scripts/check-bisect-coverage.py`，规则 P-218）。
写这类工具本身也有三个同形坑：拿账本当飞行记录、按哈希 join 但账本存的是截断路径、
用 plain UTF-8 读带 BOM 的 `boot.json`。

### 第 4 步：中途结论必须能被下一格推翻

每写一条结论，都要同时写清它**依赖哪几格**。新格子一到就重算，不要用叙述惯性保住旧结论。

判断一条中途结论是否"可推翻"的标准：能否说出"哪一格的什么结果会让它作废"。
说不出来的，那不是结论，是印象。

### 第 5 步：矩阵收敛后别停在"谁是真凶"

二分给的是**范围**（哪几块一起才死），不是**机制**（死在哪一行）。

- 范围 → 用来设计下一个观测点（把死因从"某处"推到"某行"）。
- 机制 → 靠 panic 行、寄存器值、日志里的一条具体地址/长度/错误码。

两者缺一不可：只有范围，修法是猜的；只有机制，不知道是谁把它引到那里。

### 第 0 步（前置）：拆分编译单元时先查跨文件 static

把上游同一个编译单元拆成多个文件时，会出现"调用了别处的 static 函数"这类错误。
编译器只抓得到**未声明**，抓不到**同名但语义不同**。所以修完报错那一处之后，
还要对全部 static 做一次同名审计（列出每个文件的 static 定义，再查全树是否有同名引用）。

这和第 4 步是同一个毛病的两种形状：**用名字/计数代替语义**。

## 二、三个反例（本轮三条被推翻的结论）

三条都出自同一条线、同一批格子（四个 hunk 的 15 个非空子集，飞了 11 格）。
每条按"原结论 / 依赖哪几格 / 哪一格推翻了它"写。

### 反例 1：「h2 是必要条件」

- **原结论**：能起的三张（h12 / h23 / h124）都含 h2，所以 h2 是"不再 silent"的必要条件。
- **依赖哪几格**：h1、h3、h4、h13、h12、h23、h124（当时已飞的 7 格）。
- **被哪一格推翻**：h2 单独那一格（构建于 `540f51b` 之后同批，证据
  `E:\k60-work\evidence\usblog-20261116-044817`）——不含 h1/h3/h4 也能起。
  它证明 h2 既不必要、也不充分；真正必要的是三者齐备。
- **教训**：从"含 h2 的都起"推不出"h2 必要"，因为当时**没飞过不含 h2 的单格**。
  这正是第 3 步说的洞：缺的那一格正好是决定性的。

### 反例 2：「致命集是 h3 × h4」

- **原结论**：h34（`2cdb459`）如果 silent，则致命集是 {h3, h4} 的交集。
- **依赖哪几格**：h124 起 + h123 未飞（当时 h123 已构建、没飞）。
- **被哪一格推翻**：h34 实飞（`E:\k60-work\evidence\usblog-20261116-014536`，SpringBoard 128）
  —— 能起。同时补飞的 h123（`E:\k60-work\evidence\usblog-20261116-043650`，0 字节）silent，
  说明致命集在 {h1,h2,h3} 上，与 h4 无关。
- **教训**：一条结论如果建立在"另一格还没飞"的空白上，它就不是结论，是等待验证的假设。
  当时把它写成结论，等于用叙述惯性代替了那一格。

### 反例 3：「致命集必须含 h4」

- **原结论**：h124 能起、h23 能起，而全量 silent，于是推断 h4 是致命集的必要成员
  （"全量比 h124 多的就是 h4"）。
- **依赖哪几格**：h124、h23、全量（3 格）。
- **被哪一格推翻**：h123（`540f51b`，silent）与 h34（能起）一起——h123 不含 h4 却 silent，
  h34 含 h4 却能起，两个方向同时否证。
- **教训**：「全量 − 某个能起的子集」只给出**候选**，不给出必要性。必须两个方向都有一格：
  去掉它仍死（说明不必要）、加上它仍活（说明不充分）。

## 三、一条给写文档的人的话

矩阵收敛之后，把"每一格的判据列"（例如存活计数、日志字节数、关键行有无）
和"两条结论"一起写进矩阵表，而不是只写"哪几格死"。
用计数代替语义（P-204 的同形坑）会让下一轮的人重新推一遍。

引用本文档时请连同三个反例的 evidence 路径一起引用——只引用结论，等于把"可推翻"
这一步又省掉了。
