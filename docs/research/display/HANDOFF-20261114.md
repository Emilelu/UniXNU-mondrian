## 判据怎么读（用 judge 脚本，不靠肉眼）
`python3 scripts/check-backlight-log.py <console.log>` 对 brightness-11 的日志；
`python3 scripts/check-backlight-log.py <console.log> --control=1` 对 brightness-12 的日志。
输出 PASS / FAIL / INCONCLUSIVE，判据是 conformance/control 值、stats[0]（3 或 4）、
request[4]/[5]、sig=11 计数为 0、first frame presented 出现；缺字段只记 WARN。
它已能把 brightness-4 的真实日志判成 FAIL（1 次 sig=11、无 first frame、SpringBoard 7 行）。
缺字段的判定是不对称的：默认形态缺 `conformance`/`control` 只记 WARN，
`--control=1` 模式缺这两个字段直接 FAIL（旧构建不可能发布过 control，缺就是飞错镜像）。

判读直接用 `python3 scripts/check-backlight-log.py <console.log>`（默认形态），

## 构建期间的两条硬教训（2026-11-15 实测）
1. **构建窗口内不要改任何被 git 跟踪的文件**。brightness-7/8 的 kernel 都编成功了，却都在 payload 步骤被 registry 拒：iron-2/hard-5/hard-10/hard-11 报「N tracked file(s) modified but not committed」。registry 在 payload 前会重跑，跑一次构建要 8～10 分钟，尾段才发现白费。
2. **构建开始前一刻必须 git fetch + rebase**。别的线一直在推 main：brightness-8 就是构建过程中 main 前进了 1 个提交，payload 被「HEAD is 1 commit(s) behind origin/main」拒掉。做法是 fetch → rebase → 同步 device input → 立刻起构建，中间不插入任何编辑。
