# 第一章 根卷认证与 launchd 执行链（合并 U7 + U1 + U2 + U8）

## 1.1 本章结论

当前 panic 的直接机制已经完全查明：`bsd_init()` 根挂载尾部对 `rootvnode` 发 `FSIOC_KERNEL_ROOTAUTH`（`_IOW('h',51,uint32_t)` = 0x80046833）ioctl，由 prelink 的闭源原厂 APFS kext（v2142.140.9）实现，对未密封卷返回非零（实测候选 EAUTH=80），命中 `autherr && !owner_authorized && !pong_development_root` 即 panic（补丁树 `bsd_init.c:1087`，上游 tag 同位置 908-925）。而 `pong_allow_unauthenticated_root=1` 在已刷 10-28 内核上**必然失效**：旧版补丁 gate 含 `PE_i_can_has_debugger(NULL)`，该函数只返回 `debug_enabled`，其唯一来源是设备树 `/chosen` 的 `debug-enabled` u32 属性——mondrian 主构建生成的 ADT 恰恰没有它，且不存在任何能替代的 boot-arg。修复动作是**给 ADT 注入 `debug-enabled=1`**（profile.toml `[adt."chosen"."u32"]` 一行）或**直接用当前 series 重建**（设备仓 68504b3 已把 root 侧 debugger 条件删掉）；同时 kernel_args 追加 `cs_enforcement_disable=1` 以解锁后续 userspace 的代码签名放行。root 放行之后的下一个真闸门是 `execve("/sbin/launchd")`，最优通行证是注入 20G81 原厂静态信任缓存（机制无 ECID/nonce 绑定、UniXNU/DarwinBoot 管线已齐），`cs_enforcement_disable=1` 与 amfi 三级流水线（TC→CoreTrust→amfid）是备胎；AMFI 在当前构建中的实际在场状态是最大的待验证变量。

## 1.2 PE_i_can_has_debugger 判定链与修复动作（最高优先）

### 判定链（全部源码级复核）

1. `PE_i_can_has_debugger(uint32_t *debug_flags)`（pexpert/arm/pe_init.c:631-644）：函数体 9 行，NULL 参数时直接 `return debug_enabled`；**不读 PE_state、不读任何 boot-arg**。
2. `debug_enabled` 声明为 `SECURITY_READ_ONLY_LATE(volatile uint32_t) = FALSE`（pe_init.c:52）；全内核唯一写点在 `PE_init_platform()`（pe_init.c:421 起的函数体内，复核修正：非 `pe_identify_machine()`）里 `SecureDTLookupEntry(NULL, "/chosen")` + `SecureDTGetProperty(entry, "debug-enabled", ...)` 后 bcopy（pe_init.c:481-495），uint32 非零即真。
3. boot-arg `debug=0x144` 只写另一个变量 `debug_boot_arg`（osfmk/kern/debug.c:326 `TUNABLE(unsigned int, debug_boot_arg, "debug", 0)`），与 `debug_enabled` 无关；0x144 = DB_NMI(0x4) + DB_ARP(0x40) + 0x100（废弃位）。候选 boot-arg 逐项判定（U7-C5）：`debug=0x14e/0x144` → 无效；`cs_debug=1` → 仅代码签名 verbose 打印；`-x` → `boothowto |= RB_SAFEBOOT`（不建议）；`-s` → `RB_SINGLE`。**ARM64 8796 上不存在任何能让 `PE_i_can_has_debugger` 返回真的 boot-arg。**
4. 消费点①（root 放行）：旧版 zzzz 补丁 gate 为 `pong_allow_unauthenticated_root==1 && PE_i_can_has_debugger(NULL) && vfs_flags(mount)&MNT_RDONLY`（构建树 bsd_init.c:1079-1081）；消费点②（CS 放行）：`cs_init()`（kern_cs.c:163 起，`STARTUP(CODESIGNING, STARTUP_RANK_FIRST)`）169 行 `if (disable_cs_enforcement && PE_i_can_has_debugger(NULL) != 0)` 才关闭 system/process enforcement，PONG 段 `cs_library_val_enable` 解析（190-196）同样包在 debugger 检查里。默认值两种编译分支下 system enforcement 均为 1（kern_cs.c:95-99），arm64 iOS（MASTER.arm64 含 `config_enforce_signed_code`）process enforcement 默认 1。
5. 实测证据：`artifacts/kernel.macho.adt`（10-28 实际 payload ADT）无 `debug-enabled` 串；profile.toml:58 `[adt."chosen"."u32"]` 段无该属性；board.toml:74 `kernel_args=["-v","native-ufs=1","pong_allow_unauthenticated_root=1","debug=0x144"]` → `PE_i_can_has_debugger()=0` → `pong_development_root` 恒 0 → 下次启动原样 panic 且不会出现 `PONG DEVELOPMENT` 打印。产物侧实锤：已刷 kernel.macho（10-28）内 `bsd_init.o` 反汇编含重定位 `ARM64_RELOC_BRANCH26 _PE_i_can_has_debugger`，即实测内核 = 带 debugger 检查的**旧版**补丁。

### 修复动作（方案 A + B 并行推荐）

- **方案 A（正规，ADT 属性注入）**：在 `~/hackios/UniXNU/profiles/os/ipados-16.6.1-20G81/profile.toml` 的 `["adt"."chosen"."u32"]` 段（58-64 行，现有 certificate-production-status 等 6 项）加一行 `"debug-enabled" = 1`；或在设备仓 board.toml 顶层加 `[adt."chosen"."u32"]` 覆盖。devicetree.py:334 `chosen += typed_properties(platform.get('chosen',{}))`（u32 → `struct.pack('<I')`）会把它写进 `/chosen`。pong 参考链路本来就传 `--development-debug`（build-pong-prelinked-boot.py:137 → make-pong-adt.py:145 写 `('debug-enabled', struct.pack('<I',1))`），pong_adt_contract.py:64/73/75/126 还强制校验 "Development security options require /chosen/debug-enabled=1"——board.toml 主构建可把契约校验纳入。**副作用：一次性解锁 rootauth 放行与 `cs_enforcement_disable=1` 两条链。**
- **方案 B（补丁替代，已提交）**：设备仓 commit 68504b3（2026-10-30 00:45，"k60: gate the unsealed root on read-only alone"）已把 series 第 68 行 `zzzzzzzzz-pong-development-root-policy.patch` gate 里的 `PE_i_can_has_debugger` 条件删除（b104318 修 hunk 计数）。**直接用当前 series 重新构建内核并刷机即可消 root panic，无需再改代码。**
- **方案 C（保底）**：打补丁在 PONG 下强制 pe_init.c `debug_enabled=1`。

# 第二章 APFS 只读未签名根卷（U4）

## 2.1 本章结论

K60 的 OS 卷直接来自原厂 IPSW 的 OS dmg，pong 在 QEMU 上实测该卷 Sealed=No、无 root hash/manifest 元数据（SSV 的 seal 本应在设备恢复时由 Apple 工具链建立），因此在「不重新签名」前提下卷不可能被认作 authenticated，`FSIOC_KERNEL_ROOTAUTH` 必然返回非零；autherr 最可能为 EAUTH(80)——apfs 二进制内 `authenticate_root_hash` 对『需要认证但 seal 失效』的原生返回码就是 0x50=EAUTH，且 ioctl 分发点（对 0x80046833 的比较）已被反汇编定位，确切值由现有补丁的 `printf("APFS rootauth error=%d")` 一次真机启动即可确认。放行后只读根卷本身可用：unsealed 卷本来就不做文件级 hash 校验，只读挂载也无需 seal-break。强化路径是 XNU 原生支持的静态信任缓存：内核从 DT chosen/memory-map 的 TrustCache 属性加载原厂 TCv2 缓存（此路径无 ECID/nonce/Image4 签名校验，由 prelink 的 AMFI 解析），UniXNU/DarwinBoot 链路已实现，只差打开 CONFIG_XNU_NATIVE_TRUST_CACHE（复核时已是 y）并解决 AppleImage4 startfunc 被跳过导致 img4if 未注册的问题；注意 trust cache 不参与卷认证，它是 launchd/exec 代码签名链的通行证（与第一章交汇）。

# 第三章 AppleARMPE vs ArmDTPlatform（U3）

## 3.1 本章结论

关键事实修正：AppleARMPE（IONameMatch="AppleARM"）在 K60 上从未匹配、从未作为平台专家启动——K60 的 DT root name 是 "device-tree"，由 ArmDTPlatform（IOProbeScore=5000）独占匹配，任务书「排除 AppleARMPE」的前提不成立。AppleARMPlatform kext 里真正活着的只有 AppleARMCPU（已被 0340+ArmCpu score 2000 双保险拦截）和 AppleARMBootPerf（实测报两行 Error 后继续，不 panic）；ApplePMGR/AppleARMWatchdogTimer/AppleIISController/AppleM2ScalerCSCDriver 全部因 IONameMatch 无对应节点而不 start，其中 ApplePMGR 可作为永不执行的死组件保留，天然充当 AMFI 依赖的 stub。真正的「必须工作否则卡死」只有 NVRAM：AMFI 会 `waitForMatchingService("IODTNVRAM", -1)` 无限等待。保留 AppleARMPE 路线需伪造整套 Apple PMGR/perf/clock ADT（SM8475 无对应硬件，不可行）；IOGPUFamily 对 AppleARMPlatform 零符号引用、Apple 的 DVFS 栈在本平台无论如何都不工作，两条路线对 GPU/显示/电源管理功能等价，差异只在工程债——建议维持「死组件+0340」现状，并用一个 3 条指令的字节补丁消除 AMFI 每次 boot 空等 30 秒 ApplePMGRNub 的问题。

## 3.3 可执行动作清单

1. **维持现状**：死组件（ApplePMGR 等）+ 0340 补丁 + ArmCpu score 2000 双保险；不为「排除 AppleARMPE」做任何事；**不要改 root name**（保留 "device-tree"）。

## 3.4 需实测项与资料缺口

**需实测项**：AMFI 的 30 秒 ApplePMGRNub 空等是否在真机 boot 时间线上可见（AMFI 加载日志与下一条内核日志之间量 ~30s 停顿），以及发生在 AMFI::start 主线程还是异步上下文；0340 放行 + cpus=8 时 AppleARMCPU 是否因 ArmCpu probe 全胜而完全不再实例化；若执行摘除手术，prelink 布局变化后 emit_prelink autoslide、0340 等按 RVA 的 kext 补丁是否被自动重定位，IOGPUFamily/IOMobileGraphicsFamily/IODARTFamily 运行时是否触发被重定向的 __got；AppleImage4 是否仍需要 /chosen 或 /default 下 chip-epoch、security-domain 属性（缺失 panic 0x60，iOS 12/A11 时代报告）；U3-C13 补丁上机后 AMFI 启动路径是否正常（waitForMatchingService timeout=0 语义需实测）。

# 第四章 WiFi / 音频 / 蓝牙（U9）

## 4.1 本章结论（含优先级建议）

K60 的 WiFi 芯片是 QCA6490（stock DT 节点 qcom,cnss-qca6490，MHI/QRTR dev-id=0x1103 与 mainline ath11k 的 WCN6855_DEVICE_ID 一致），走 PCIe0 而非 SNOC；iOS 16.6.1 内核里的 WiFi kext 全是 Broadcom 系（IO80211Family+AppleBCMWLANCore，Apple 自写驱动、非 DHD 系，与 Broadcom 芯片/固件交互），对 WCN6855 无效，prelink 也没用——可行路线是自研，且同生态 UniXNU-sheng（SM8550 小米 Pad 6S Pro）已用 Ath12kWifi+WifiProbe+WifiNet 跑通 WiFi，其 PCIe0 寄存器窗口与 GPIO 组和 K60 逐项相同，可直接移植。音频上任务书假设的「WSA883x 功放」与 K60 DT 事实**矛盾**：K60 是 ADSP+WCD938x+2×AW882xx I2C 智能功放（wsa-max-devs=0），sheng 的「内核 AudioReach(GPR)+ADSP 固件(modem_a)+用户态 AudioServerPlugIn 替换 /System/Library/Audio/Plug-Ins/HAL」路线已 implemented 可照抄。蓝牙是 QCA6490 走 GENI UART（BT_EN=GPIO81），XNU 开源树无蓝牙子系统、UniXNU 生态零先例。

**优先级建议：WiFi（最容易先做通）> 音频 > 蓝牙。**
- **WiFi 第一**：有 sheng 端到端先例（含 iOS 用户态接线的 Apple80211 ioctl 垫片）、ath11k 全开源参考、板级寄存器/GPIO 与 sheng 逐项对齐（PARF 0x1c00000/DBI 0x60000000/ATU 0x60001000/config 0x60100000；WLAN_EN=80、BT_EN=81、SW_CTRL=82、PERST#=94、WAKE#=96），依赖链最短；唯一硬缺口是 Ath12kWifi 组件需为 WCN6855 hw2.1 增加 ath11k 后端定义（dev-id 0x1103≠ath12k 0x1107）。
- **音频第二**：先例完整（sheng 三层 implemented）但依赖 ADSP/GPR/GLINK/SMEM/SMP2P 移植与 trust-cache 签名链（payload 无 trust cache——profile.toml:37 "No text fixups and no trust cache yet"），且 CoreAudio 24MHz host clock 需改 dyld 共享缓存页。
- **蓝牙最后**：协议最简单但零先例、XNU 无蓝牙子系统、无 Apple 用户栈可复用（CoreBluetooth 不可用），「能用」价值最低。

另注意：K60 在 postmarketOS 仍 not booting（仅 U-Boot 二级引导可用），不存在可直接抄的 mainline K60 板级文件。

# 第五章 Goodix 触摸与 GENI-SPI（U5）

## 5.1 本章结论

协议与控制器两层答案已全部对上权威源：K60 的 DT compatible 就是 goodix,gt9916（Berlin-D），本机补丁 0242/0251 的 Berlin SPI 帧（读 0xF1+4 字节大端地址+3×0xFF dummy、chip ID 在 0x10014 头 4 字节 "911\0"、触点 8 字节 stride）与 mainline Linux goodix_berlin_spi.c/goodix_berlin_core.c 逐字节一致，GT9xx 备用 ABI（0x8140="9111"/0x814E/0x8150）与 mainline goodix.c 一致。无 RSC 的 GENI-SPI 最小初始化 0241 已实现且与 mainline gcc-sm8450.c/geni-se 逐寄存器核对通过：GCC +0x62008 的五个 vote 位是纯 MMIO 寄存器（mainline clk 驱动自己也是直接写，不经 RPMh），SE4 ready 判据 = FW_REVISION_RO(0x68) 高 8 位=1（SPI 固件）+ FIFO 深度非 0 + GENI_STATUS(0x40) bit0=0。真正没解的是**电**：UEFI(mondrianPkg) 无任何 SPMI/PMIC 驱动、DSDT 无 regulator 内容，ldo2 只能指望 ABL 留电（热重启可判别）；SPMI 直写在工程上缺 ldo2 外设基址且 observer 通道只读，当前不可落地。stage 3/4/5 从未上机，下一步就是按 board-touch.conf（k60touchstage=4 k60rpmhoff=1 k60touchid=1）读一次 ID。

# 第六章 120Hz 显示（合并 U6 + U10）

## 6.1 本章结论

自研显示驱动（MiniIOMobileFramebuffer，即任务书所称自研 AppleCLCD）已不是硬编码 60Hz：kFBRefreshHz=60 是默认值，boot-arg `fb_hz=N`（1..240）即可改写 TimingElements 的 SyncRate/PreciseSyncRate（16.16 定点）与 vsync 定时周期，内核侧 120Hz 只差一个 boot-arg——但该驱动是**纯软件 framebuffer**（CPU memcpy 到 ABL 点屏留下的 boot framebuffer），0210 补丁与 89 条补丁集内没有任何 DSI/PLL/MDSS 代码，真实面板刷新率由 ABL 点亮的档位决定（UEFI SimpleFb 只包 GOP，内核直吃 splash framebuffer）。K60-120HZ-PLAN 的面板数据全部取自错误对象：其引用的 120/60 双档与 0xC6=0x1244/0x1288 切档来自 Qualcomm 通用参考面板 sharp_qhd_plus_dsc_cmd，而 K60 真实面板 m11a_42_02_0a_dsc_cmd（fdt19 fragment@83）经复核实测有 **60/90/120 三档**（timing@0=60Hz 切档 DCS 0x2F=0x02、timing@1=90Hz 0x2F=0x01、timing@2=120Hz 0x2F=0x00，三档 phy-timings 与 clockrate 0x47868C00=1.2GHz 逐字节相同）——120Hz 档原生存在，PLAN 的"无 120Hz 档/需自行构造"结论已被修正。ProMotion 识别不走 MobileGestalt（键表中无 120Hz 显示键），权威链是 IOMobileFramebuffer 驱动发布的 TimingElements(SyncRate) → UIScreen.maximumFramesPerSecond → CADisplayLink 上限；当前伪装的 iPad7,1 本身就是 2017 ProMotion 机型（IPSW 组名 iPad_Pro_HFR），无需换机型，任务书给的 iPhone13,2 反而是 60Hz 的 iPhone 12 Pro。DSC slice 几何与帧率正交无需改动：1440×3200@120 的 DSC 净码率 4.424 Gbps，双 DSI（8 lane）每 lane 553 Mbps，在 D-PHY 能力内；要真 120Hz 必须新增 DSI host/PHY/PLL 驱动（当前完全缺失的一整块），phy-timings 14 字节已确证为 DSIPHY_CMN_TIMING_CTRL_0..13 寄存器直写值（v4.0 D-PHY 布局），iOS 侧 CoreAnimation 读的就是 TimingElements 内 Horizontal/VerticalAttributes 的 SyncRate/PreciseSyncRate。只改 fb_hz=120 不会花屏/黑屏（DSI 完全不动），效果是 CoreAnimation 按 8.33ms 节拍绘制、显示仍 60Hz 扫描、CPU 拷贝翻倍、撕裂概率升高。

## 6.3 可执行动作清单

1. **P1 软件侧（立即可做）**：board.toml [payload] kernel_args 追加 **fb_hz=120**——TimingElements SyncRate/PreciseSyncRate=0x780000、vsync 周期 8.33ms、CA 节拍 120Hz，无需改任何 C 代码；预期画面仍 60Hz 扫描（预期管理见 U10-C12）。
2. **重写 PLAN 面板数据**：以 fdt19 fragment@83（m11a_42_02_0a）为准重写 K60-120HZ-PLAN 第 2/3 节；弃用 sharp_qhd_plus 的 0xC6 切档序列；120Hz 原生档 = timing@2 的 qcom,mdss-dsi-timing-switch-command（DCS 0x2F=0x00 + 0x8B=0x00）；90Hz = timing@1（0x2F=0x01 + 0x8B=0x10）。
3. **P2 运行期切档验证（先易后难）**：先验证"仅发 timing@2 切档命令 + fb_hz=120"（cmd mode 面板 GRAM 自刷新，host 仍 60Hz 比特率），真机判据 TE 频率与画面连续性；DCS long packet 照抄 dtbo 全部 52 字节 payload，不要只发 3 字节。
4. **P2+ 新增 DSI host/PHY/PLL 驱动（当前完全缺失的一整块）**：实施顺序①DSIPHY_CMN_TIMING_CTRL_0..13=目标档 14 字节（整体照抄，TIMING_CTRL_12/13 clk_pre/clk_post 必须一起换）②DSI PLL 重锁（bitclk 约 550-621 Mbps/lane@120Hz，5nm PLL 能力内、4 lane 不变）③切档 DCS ④fb_hz=120；slice 参数（720×32/slice-per-pkt=2/bpp=8）与帧率正交，不动。
5. **机型不动**：维持 iPad7,1/J120AP（本就是 ProMotion 组 iPad_Pro_HFR）；ProMotion 能力由 TimingElements（fb_hz）表达。
6. **文档口径纠正**：面板是 dsi_cmd_mode（带 TE），非 PLAN 引用日志所说的 video mode；"DSC video mode" 是自造日志串。

## 6.4 需实测项与资料缺口

**需实测项（合并 U6/U10）**：m11a 面板 120Hz 档真机可用性（dtbo 已确认原生三档，剩余问题是切档命令下发通道与 DSI PLL 位率——原"dtbo 只有 60/90 与官方 120Hz 规格矛盾"的疑团已由复核解除）；fb_hz=120 实测：TimingElements 报 120 后 backboardd/CoreAnimation 是否真正按 120 节拍跑（抓 refresh notification 日志频率）与 UIScreen.maximumFramesPerSecond 的 userspace 实际返回值；timing@2 切档的 DCS 序列能否在内核侧下发：DSI controller 0xae94000 的通道是否被 ABL/UEFI 遗留状态占用（参照触摸 RSC 0x17a00000 硬阻断先例），切档后 splash framebuffer 连续性（无闪黑）；DSI PLL 当前位率（决定 90Hz 是否免重配即用、120Hz 需要什么）——需真机读 DSI PHY PLL 寄存器或从 ABL 日志提取；qcom,display-topology <2 2 1> 的第三元语义（单/双 DSI）——决定 120Hz 每 lane 码率是 1.106 还是 0.553 Gbps；切档命令只发、不动 PLL/MDP/TIMING_CTRL 时 cmd mode 面板是否真以 120Hz 自刷新（TE 频率、DSI host 是否报溢出/underrun）；画面撕裂可感度与 present 队列（fb_queue=2）是否够用；ABL 上电用哪档 timing 与面板上电默认帧率。
