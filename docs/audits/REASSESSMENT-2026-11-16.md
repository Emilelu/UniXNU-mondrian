## WiFi: c7 evidence boundary

Source: `E:/k60-work/evidence/usblog-20261116-122546/console.log` (3,367 lines, 227,186 bytes, SpringBoard 128, no panic marker), image `wifi-20261116c7` (`4d187a71c4d3e0931e4e90353e69efd53c93e61a00b56e09817aeadf47a1f45f`). The log reports hardware `exec_env=1`, `mhi_state=1`, `MHISTATUS=0x101`, `MHICTRL=0x200`, while the driver's cached `ee=0`; it reports an MHI timeout `-110`. The device-side execution environment and the driver's cached state are distinct observations.

The c7 `irq entered` line is not proof of hardware MSI: the compatibility runtime's `lx_irq_raise_all()` marks every registered IRQ pending during its pump. Conversely, c7's missing `MSI delivered` line is not proof that MSI did not arrive. In the actual WiFi source, `nw_wifi_start()` failure returns through `goto done`; the `MSI delivered` counter is checked later in the runtime loop, which is never entered after the c7 `-110` failure. Thus the diagnostic was not reached on this failure path. The event-ring `rp` equality is also not by itself proof the device did not write: initialization, shared memory, and cache attributes need to be distinguished before assigning the writer. No root cause is established.

The c8 owner's subsequent offline review (`82086f1069717f269c47ef194b02f660d9f0d3ef`) identified a reachable delayed second AMSS call: transition items are not deduplicated, and a queued SBL worker can download again after the proactive PBL path returns. The direct call also discards the download return value. Those are source-level findings, not evidence that the device executed a second transfer. The owner's historical build/flash logs selected six other active items and omitted parked WiFi; `eight_step_items=all` did not establish WiFi coverage. Current source/archive consistency was recovered, but temporary native-builder changes and mutable intermediate symlink targets prevent an immutable reconstruction of the historical build. c8 remains held. For an allocation of 5,296,128 bytes with 524,288-byte segments, the calculation is 11 data buffers (10 full plus 53,248 bytes) and one vector-table buffer: 12 entries and 11 vectors, not 11 total entries. This calculation is not a c7 measurement.

The `iova_start=0` setting is a configured MHI address aperture/envelope; it must not be described as a physical-zero context base. Channel/event/context base registers are independently populated from DMA addresses. c8's report and MHI state-machine note need correction: the proactive AMSS branch changes behavior, and `exec_env` becoming 2 would mean the device reports AMSS execution environment, not that WiFi is fully operational. Full WiFi still requires downstream MHI/ath11k initialization, firmware, network-device, association and data-path evidence.

## Bluetooth: d7 evidence boundary and gate scope

Sources: `E:/k60-work/evidence/usblog-20261116-130444/console.log` and `E:/hackios/k60-bt/patches/xnu/0514-k60-bt-boot-observability.patch`. d7 reached `boot: rampatch done`, then later logged `boot: budget exhausted at op=0xfc00 waiting=1`, `QCA Failed to send TLV segment (-60)`, and `power=1 result=-60`. This proves that the overall boot budget expired while that command was marked waiting. It does **not** prove the NVM's first segment was stuck, that all 27 theoretical segments had or had not been attempted, or that no individual command completed. The global-budget check precedes the per-command timeout check; a pump/wait can cross both deadlines before the next check, so absence of `command timeout` does not prove every segment returned within 10 seconds. Per-segment d8 counters are useful observation, but their timing overhead and counter semantics must be accounted for.

The d8 artifact has a valid manifest and image audit. However, the branch's `docs/research/EIGHT-STEPS.toml` still marks Bluetooth `parked`; `scripts/eight-step-gate.py` filters parked hardware from flash checks. The green flash preflight therefore did not cover Bluetooth. The image must not be flown until the owning branch activates the hardware item, refreshes its step evidence/prediction for the observational experiment, and demonstrates that the actual `--flash` gate includes Bluetooth. This is a gate-scope defect, not an artifact-hash defect. This review also fixes the README renderer so parked items are explicitly labeled, `verify.done=false` cannot render a completed verification merely because three strings exist, and readiness requires all seven prerequisites. Six fixture tests exercise those rules and bilingual generation/checking. This presentation fix does not change the flash selector or authorize any image.

## ADSP: early publication bypass

In the audited plan-C revision before the refusal fix, the rail check protected only the later legacy path. The early `pong_handoff_publish=1` call in `IOKitBSDInit` ran before Data mount, claimed the startup owner and entered resource acquisition/owner stages; the call graph could reach SMEM mapping/allocation, PAS image setup and SCM `AUTH_AND_RESET` without the rail-inheritance result from `k60_adsp_bring_up()`. The following refusal fix changes that path's behavior; this paragraph records the original defect, not a bypass in the corrected revision.

The required guard must reject an unmeasured/invalid rail state **before the earliest side effect that reserves resources or reaches PAS**, not only before `AUTH_AND_RESET` in a different late path. Simply moving publication later also affects startup-owner claims and the battery consumer: `k60_physical_battery_start()` marks its one-shot attempt before reading the handoff, so a late publisher needs an explicit deferred consumer notification/retry design. The owner has now restored `resources_cb()` to `K60BoardUnsupported` without setting `resources=1` (source at `E:/hackios/k60-adsp-handoff/drivers/PongPower/K60AdspBoard.c:241-255`). The host suite was reported exit 0, not rerun by this review; Native arm64 was syntax-checked, not executed. This closes the identified declared-only bypass in source/host evidence. It does not establish rails, a working late publisher, or a valid battery consumer lifecycle. The owner reports 80 identical pre-existing path-check failures in candidate and baseline; these remain failures, not a full-gate pass. Do not build or boot a functional publish image until the remaining design and gates are satisfied.
