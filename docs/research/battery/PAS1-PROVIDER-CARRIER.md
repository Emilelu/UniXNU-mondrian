# PAS1 image carrier decision

> Status: carrier research for feat/adsp-handoff-owner, 2026-11-15. The staged owner/provider APIs exist, but the production carrier and platform PAS/SCM/resource backend do not. This document compares input carriers only; it does not claim PAS1, GLINK, battery, audio, or charging works.

## Decision

Prefer evaluating a kernel-embedded read-only firmware bundle (option B) for the early k60_owner_image_reader. It reuses the repository's existing Metal blob-generation precedent and avoids adding a new UEFI DXE, a fixed physical reservation, or an unimplemented ADT handoff. This is a design preference, not approval to implement or evidence that a blob has been linked for ADSP. Lead owns the production carrier. Keep the owner unavailable until the real reader, PAS backend, resource votes, and exclusion are installed and meet the provider contract.

The captured image inputs are 26 files totaling 23,505,092 bytes on disk: adsp.mdt (5,404 B) and 25 present adsp.bNN pieces (23,499,688 B). The complete directory scan found 28 files / 23,506,308 B, including two non-image files. Piece b24 is absent because its segment is pure BSS. The older ADSP-CARRIER.md figure “26 files, 23,494,284 bytes” is the sum of segment file payload copied into memory, not the sum of carrier files; its byte total needs correction before reuse.

The independently summed 0612 segment table has 24 load segments: 23,494,284 bytes of file payload copied and 25,925,684 bytes zero-filled, for a 49,419,968-byte (0x3100000) mapped span. The 23,505,092-byte disk bundle exceeds copied PT_LOAD payload by 10,808 bytes: the piece files exceed segment payload by 5,404 bytes because b00 is the 884-byte ELF-header prefix and b25 is the 4,520-byte hash block; adsp.mdt is a second copy of that 5,404-byte metadata. BSS adds 25,925,684 bytes only to the runtime mapped span and contributes no disk bytes. Segment 10 is { 0x86e0b2c0UL, 720, 2672, "adsp.b10" }; its destination is not page aligned, so the loader must honor exact byte offsets/lengths rather than page-aligning or rounding individual copies. The 0612 generated table is fixed at link base 0x86300000 and is not the current relocatable planner; use it only as a reference for copy/BSS arithmetic, not as a loader implementation.

## Reader contract

The production callback declaration is:

~~~c
typedef int (*k60_owner_image_reader)(void *context, K60OwnerImage *image);
~~~

K60OwnerImage supplies a borrowed pointer and byte count for the immutable MDT, a K60AdspMdtPiece callback/context for indexed pieces, an opaque non-null pin handle, and a writable metadata buffer with its capacity. Return exactly 0 only when every field required by the captured MDT is valid and the image is pinned; return nonzero for unavailable, malformed, incomplete, or failed input. A nonzero callback result is normalized by stage 1 to owner-unavailable (-1000); because the owner only calls image_close after a successful reader return, the reader must clean up any partial open/pin itself before returning failure. The owner runs the bounded MDT parser before exclusivity acquisition and before SMEM/TCSR mapping; malformed bounds, missing piece, or exact-size mismatch therefore fails closed without AUTH. The successful pin must remain immutable and valid through every segment copy, BSS operation, cache synchronization, and AUTH decision, not just through the parser call.

The reader must:

- Keep the MDT bytes and every required piece stable for the full image lifetime. Pin/open them consistently so a generation cannot change between MDT metadata and piece reads; image_close releases only the handle acquired by a successful reader, and is called once on safe abort. Poisoned or published ownership retains the image pin.
- Implement the indexed K60AdspMdtPiece(void *, uint32_t index, const uint8_t **, size_t *) callback as a bounded, read-only view. It returns success only with a non-null buffer of the exact planned p_filesz for that piece. Missing files, short reads, truncation, stale metadata, overflow/out-of-range indices, or wrong lengths return failure; never report success with a partial buffer. Any storage-specific chunking must finish and validate the complete piece before exposing it, or retain an immutable backing object whose exact range is available for the subsequent load.
- Provide non-aliased writable metadata storage with enough capacity for the validated prefix plus hash payload. For the captured image this is 884 + 4,520 = 5,404 bytes. Respect parser bounds and do not point the metadata output into the MDT or any piece buffer.
- Perform no hardware access, PAS/SCM call, SMEM/TCSR mapping, boot-argument mutation, or fabricated availability/ownership reporting. Carrier availability is one input to the later platform backend, not proof of authentication or GLINK readiness.

The old K60AdspRead(const char *part, void *dst, uint32_t bytes) in patches/xnu/0612-k60-adsp-image.patch:122 is the same conceptual source-reader boundary: named image part in, exact requested bytes out, zero for success. It is not ABI-compatible with the new reader. K60AdspRead copies into a caller-provided destination in one callback; K60AdspMdtPiece returns a const borrowed pointer and size for a numeric MDT program-header index. A production adapter may wrap files/blob storage in the new interface, but it must preserve exact lengths, errors, immutable lifetime and pin semantics. The old 0612 implementation's generated fixed-address table is not the current relocatable ELF planner.

## Captured-image host fixture

The existing parser test scripts/tests/test-k60-adsp-mdt.py:249-272 can validate the captured MDT and piece inventory offline. It checks MDT SHA-256 1238098817957c4d3cd0995fd413332751ac8082ea315e6e1d9bdb247cadc694; 26 program headers, 24 load segments, hash index 25, prefix 884 B, hash 4,520 B; exact metadata concatenation of 5,404 B; 23 payload-piece callbacks because segment 24 is BSS-only; relocatable span 0x3100000 from link base 0x86300000 to configured physical range [0x9fd00000, 0xa2e00000). The full destination buffer is not allocated or touched by this parser test.

A fake-reader stage test should use these same immutable captured inputs and exercise the reader boundary without pretending to implement the physical carrier. Minimum cases: all MDT/pieces present and exact-size; each required piece missing; short/truncated MDT; short/oversized piece; callback error; out-of-range index; metadata capacity too small; pin invalidation attempted before load; stable pin through all 23 nonzero copy callbacks and the AUTH attempt; and one successful safe-close path. Assert failures stop before AUTH and before any SMEM/TCSR/PAS callback. Fake memory copy can verify the parser plan's 24 destinations, 23,494,284 copy bytes, 25,925,684 zero bytes and exact b10 720-byte placement; this validates host orchestration and arithmetic only. It cannot prove that firmware storage is available during boot, bytes are authentic/trusted, a physical ADSP write/cache maintenance occurred, SCM/PAS authenticated or started a processor, or hardware resources/GLINK are owned.
