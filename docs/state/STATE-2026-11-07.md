系统已进用户态，SpringBoard 已进主循环；**唯一硬阻断是 launchd（PID 1）在启动后期 SIGSEGV**，随后 `initproc exited` 触发内核 panic 重启。根因：设备上的 OS 窗口是**没跑过 `apply()` 的 stock 20G81**。

## 2. 唯一硬阻断：launchd（PID 1）SIGSEGV

device（2026-11-07）：

```
KX! <...> launchd sig=11 ns=2 code=0xb
access(/System/Cryptexes/App/usr/libexec/webbookmarksd, X_OK) failed errno 2
initproc exited
```

- `sig=11` = SIGSEGV；`ns=2` = `OS_REASON_SIGNAL`；`code=0xb` = 11。即 launchd 自己崩溃，不是 jetsam/沙箱他杀。
- `KX!` 行的格式来自 `patches/xnu/0238-k60-exit-reason-observer.patch`（`patches/xnu/series:132`）。
- 崩溃紧跟在 `access(...webbookmarksd, X_OK) failed errno 2` 之后；**直接触发点未核实**，只能确认时序相邻。
- `initproc exited` 后内核 panic 并重启；长按重启会掉 DRAM，ramoops 拿不到（§13.3）。

## 3. 根因：OS 窗口是未跑过 `apply()` 的 stock 20G81

三条设备判据：

1. 日志是 `Pong init: exec original /sbin/launchd`，不是 `/sbin/launchd.ios`。当前 HEAD 的 init 在 `userland/init.c:323-335` 固定 `execve("/sbin/launchd.ios", ...)`；日志里没有 `.ios`，说明设备上的 init/窗口不是 apply 后的形态。
2. 日志里没有 `pong/stock-config`。该目录只在 `apply()` 里创建（`userland/build.py:462-468`）。
3. 四条 `Pong init: optional boot view SKIP ...`（`userland/init.c:232-251`）指向 `/pong/LaunchDaemons`、`/System/Library/Audio/Plug-Ins/HAL`、`/Library/Audio/Plug-Ins/HAL`、`/private/var/pong/stock-wallpaper`；这些 target 只在 apply 后的窗口里存在。

结论：设备 OS 窗口仍是 stock 的 `LaunchDaemons` + stock `launchd`，pong 的 job 集和 `/pong/stock-config` 都没有落地，launchd 走到后期 SIGSEGV 是预期结果（流程见 [APPLY-PIPELINE.md](../plans/APPLY-PIPELINE.md)）。

修复路径：在 macOS 上跑 `prepare()` + `apply()`，把改过的 OS 窗口写回设备；见 §4 与 APPLY-PIPELINE。

### 13.2 `/private/var` 的真实 UFS Data 路线

- 内存盘路线（NativeRamBlock + 32 MiB APFS seed）实测死路：`K60DATA mount enter ... /dev/disk1s1` 后永久卡死，卷已发布、卡在 `mount()` 内部；pong 不走这条路。
- 正确路线：真实 UFS Data 窗口。32 MiB 裸 APFS 必须用 GPT 包裹（`PongUfsTransport` 要求 offset 512 处 `EFI PART`；裸 APFS 会被拒；SystemOS 则是 `NXSB@32`）。
- 窗口可写性由 boot-arg `pong_ufs_readwrite=1` 决定；没有它连 Data 窗口都是只读。
- 驱动窗口表由 `#if XNU_PONG_UFS_DATA` 包着，宏由 defconfig `CONFIG_XNU_OWNER_DATA_UFS=y` 精确行推导；`DATA_UFS=1` 必须 `NATIVE_RAM_BLOCK=0` + `NATIVE_UFS=1` + `DATA_MOUNT=1`。
- 挂载顺序：先 union SystemOS 到 `/`，再挂 Data；反过来 union 会遮住 `/private/var`。
- 历史 defconfig（2026-10-30，旧 32 MiB seed）：`CONFIG_XNU_NATIVE_RAM_BLOCK=n`、`CONFIG_XNU_NATIVE_UFS=y`、`CONFIG_XNU_OWNER_DATA_MOUNT=y`、`CONFIG_XNU_OWNER_DATA_UFS=y`、`CONFIG_XNU_OWNER_DATA_VOLUME_UUID="6DCCF70A-6FD6-403E-ACED-95313CD7CBB8"`；boot args 含 `pong_allow_unauthenticated_root=1`、`pong_software_keybag=1`、`disable_exc_resource=1`、`pong_ufs_readwrite=1`。当前值以 `board.toml` 为准（Data UUID 已换为 `1BCD69FF-…`）。
- 早期读写挂载卡死：`write && !hostIdle()` 返回 `NotReady`，APFS 无限重试，host 被 poison；后来 RW 已通（历史记录：`K60DATA mount returned error=0 result=0 rw=1`）。当前判定以 §1/§2 为准。

### 13.3 ramoops 在本机不可用

- ramoops 映射成功（`ro_base=0xfffffff035600000 sig=43474244 ro_size=17494`，`sig` 是 Linux `PERSISTENT_RAM_SIG` “CGBD”）。
- 但长按电源重启不是温重启，DRAM 掉电，`/sys/fs/pstore` 永远为空；`PE_k60_reset_now()` 也没生效。**屏幕是唯一可靠日志**，关键状态用 `panic()` 打到屏上。
- 历史布局：`ramoops@0xa7000000 reg 0xa7000000,0x400000`，console 2 MiB + pmsg 2 MiB，与 `zzzzz-pong-ramoops-minimal.patch` 逐字节一致；`Failed to get pstore mem` 来自 `minidump.ko`，与 ramoops 无关。

- `display-scale=3`：ADT `/chosen` 缺它 → `preferredScale=0` → `1440/0=inf` → SpringBoard 在 `FBSDisplayMode` 里主动 `brk`。已补在 OS profile（core `db7177c`）。ADT 不是标准 FDT，`dtc` 会报 magic 错，只能字节搜；历史上 `display-scale` 在 offset 9536，`len=4 value=3`。
- 资源违规刷屏：源码补丁 `patches/xnu/0230-k60-exc-resource-early-out.patch`（commit `6db2954`）在 series；二进制路径 `smp/patch-violation-printf.py` 把三条格式串首字节改 `\0`。注意二进制里还有一条不带 `error %#x` 的 `disk_writes` 文本（offset 1259407），不要误清。
- watchdogd 由 launchd disabled-jobs 策略禁用（补丁 0222）；`disable_exc_resource=1` 挡不住 `OS_REASON_SIGNAL`（namespace 2 是信号退出，SIGTRAP=5）。
- 软件 framebuffer：每帧 1440×3200×4 ≈ 18.4 MB 做 bilinear + memcpy；`fb_threads` 默认 1（`MiniIOMobileFramebuffer.cpp:165`），单核整帧 9–10 ms；boot-arg `fb_threads=3`、`k60_fontscale=3` 可观测。`fb_hz` 只改 `refreshHz()` 返回值和 vsync 周期，不改 DSI 面板时序。
- AppleARMCPU `_validateConfiguration` 的二进制补丁是 8 核启动必需；当前 `board.toml:130` 已是 `cpus = 8`。
